## 二、待修（1 项）：前端 3010 TCC EPERM 读文件被拦 ⏳

### 现象

```
curl http://127.0.0.1:3010/login.html → 超时 8s（HTTP 000）
curl http://127.0.0.1:3010/ → 302 正常
```

日志 `/Users/yanghy/.workbuddy/ai-content-frontend/frontend-3010.log` 尾部：

```
[static-server] uncaught: EPERM: operation not permitted, open '/Users/yanghy/Documents/New project/ai-content/frontend/out/login.html'
[static-server] uncaught: EPERM: operation not permitted, open '/Users/yanghy/Documents/New project/ai-content/frontend/out/index.html'
```

### 根因

launchd 托管的 3010 进程**读取 `~/Documents` 下的 out 产物被 macOS TCC 拦截**。

关键事实链：

1. 前端由 launchd 托管：`com.jiuzhang.ai-content-frontend`（`~/Library/LaunchAgents/com.jiuzhang.ai-content-frontend.plist`）
2. wrapper 让 node 执行 Documents 下的 `static-server.mjs`，`--root out` 经 `static-server.mjs:23` 的 `path.resolve(__dirname, "..")` 解析成 `frontend/out`（绝对路径，落在 Documents 下）
3. node 读 Documents 下的 `out/*.html` 时报 EPERM

> ⚠️ 注意：本机 skill `launchd-tcc-service-recovery` 里记过一条「node 读 Documents 放行、只拦执行脚本」的结论，但**当前环境已失效**——现在读 Documents 下 out 文件也报 EPERM。疑似 macOS 26.4.1 系统更新后 TCC 行为收紧，或 8/18 之后授权被重置。修复时不要依赖旧结论。

### 另一个隐患（顺带一起修）

当前 3010 进程 61549 是**昨晚启动的旧进程**，仍在用被标记删除的旧 node：

```
61549 10:38:30 .../versions/22.22.2/bin/node .../static-server.mjs
node 61549 ... txt ... /Users/yanghy/.workbuddy/binaries/node/versions/.22.22.2.deleting.4751.1788177763630/bin/node
```

它跑了 10.5 小时，node 路径是 `.22.22.2.deleting.*`（旧版本被删除前的残留句柄）。即使 TCC 修好，也应重启让新 node `22.22.2-2` 接管。

### 修复方案（参照 kaypal-proxy 先例）

本机已有先例：`kaypal-model-proxy` 曾因同样问题，把运行副本**复制出 `~/Documents`** 到 `~/.octop/kaypal-proxy/` 解决。

给 3010 的建议修法（把 out 产物迁出 Documents）：

```bash
# 1. 建非 Documents 运行目录
mkdir -p /Users/yanghy/.workbuddy/ai-content-frontend/out

# 2. 每次构建后同步 out 到非 Documents 目录（构建命令在 frontend/ 下）
rm -rf /Users/yanghy/.workbuddy/ai-content-frontend/out/*
rsync -a --delete \
  "/Users/yanghy/Documents/New project/ai-content/frontend/out/" \
  "/Users/yanghy/.workbuddy/ai-content-frontend/out/"

# 3. 改 wrapper：--root 指向非 Documents 的绝对路径
#    文件 /Users/yanghy/.workbuddy/ai-content-frontend/static-server-launchd.sh
#    把最后一行 --root out 改成：
#      --root /Users/yanghy/.workbuddy/ai-content-frontend/out
```

> `static-server.mjs` 的 `--root` 参数：源码 line 7 注释写「相对 frontend/」，但 line 23 实际是 `path.join(FRONTEND_ROOT, parseArg("--root", "out"))`，`FRONTEND_ROOT` 来自 `__dirname` 的上一级。若 `--root` 传绝对路径，`path.join` 仍会拼接出绝对路径（Node `path.join` 遇到绝对路径会重置），**需先确认 `path.join` 对绝对 root 的行为**；若不确定，可给 `static-server.mjs` 加一个「root 为绝对路径时直接使用」的判断，或改用 `path.resolve`。

**备选（更省事但每次构建都要手动同步）**：保持 `--root out` 不变，仅把 `frontend/out` 用 `rsync` 同步到 wrapper 能读到的非 Documents 位置，并让 wrapper `cd` 到那个位置。
