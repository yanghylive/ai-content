## 一、修正后的真实诊断

### 1.1 三条旅程：能力已通，缺口在「体验层」而非「打通层」

| 旅程 | 已有（后端真实存在） | 真实缺口 |
|---|---|---|
| 情报 → 选题 | `topicId` 关联、`generate-topic` API、收件箱「生成选题」按钮 | ①生成后跳转/定位不明确；②**重复点击会重复建选题（无幂等）**；③入口可发现性待评 |
| 发布 → 互动 | content→publish→interaction 归因链、统一收件箱聚合 `publishRecordId`、显示「内容来源」 | ①发布页缺「按内容反查互动」入口+筛选；②收件箱 API 缺 `contentId/publishRecordId` 查询参数；③部分采集数据走 rule_based 推断，需明确「无归因」标识 |
| 互动 → 客户 | 互动事件→Growth Lead→CRM Customer 链路（转线索 + sync-crm） | ①统一收件箱、评论获客页缺直接 CTA；②CRM 未安装/无授权/重复同步/人工确认 状态未定义、阻塞原因未展示 |

> 结论：**主链路的对象与接口基本都在，断的不是「有没有」，是「顺不顺、稳不稳、能不能点」**。

### 1.2 路由层级：一级已收敛，问题在二级的 canonical/alias 关系

- 桌面一级场景 7 个（今日增长/获客/客户/内容/互动/执行/移动设备）+ 底部「设置/我的」，结构本身合理。
- 真实问题是**二级路由的 canonical 关系未厘清**，最典型的两处：

| 冲突 | 现状 | 建议 |
|---|---|---|
| `/message` vs `/engagement` | message 是 rail 一级「互动中心」ScenePage；engagement 也有独立统一收件箱 Tab | 明确 canonical：互动正门收敛为一个，另一个做 alias 或子页 |
| `admin/*` 别名维护 | 已用 `routeAliases` 收口，但 URL 双份、权限边界、命名重复仍需维护 | 固化 alias 清单，纳入路由零丢失快照 |

## 四、验收口径（修正）

**A 类验收**（替代原「301」口径，因静态导出无 HTTP 301）：
- 旧链接可达、**查询参数保留**、无 404、canonical URL 正确。
- 若确需 HTTP 重定向，由外部 Web 服务器配 308/301，不在 Next 内做。

**B 类验收**（三条旅程的功能验收）：
1. 情报条目能生成且**只生成一个**选题（幂等）。
2. 发布记录能反查对应评论/私信，并**明确标注「无归因」**。
3. 互动事件能按 `互动 → 线索 → CRM 客户` 流转，并**正确显示阻塞原因**。
