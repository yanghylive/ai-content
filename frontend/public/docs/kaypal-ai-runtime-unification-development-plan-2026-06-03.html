KaypalAI 内容创作平台 · Runtime 统一方案 · 2026-06-03

3010 / 3011 / 5409 终极代码合并开发方案

本方案目标只有一个：完成终极代码合并。3010 保留为唯一用户界面，3011 保留为 Core API， 5409 不再作为独立项目和独立前端存在，其有效执行能力拆入 Kaypal Local Runtime。

一、6 个专家会议结论

产品负责人

用户入口

用户不应该知道 3011 和 5409。所有功能、状态、失败原因、账号配置、证据记录都必须回到 3010。

结论：3010 是唯一用户入口，不再暴露 5409 页面。

后端架构专家

业务中枢

3011 必须成为唯一业务调度层。前端不能直接调 worker，所有真实执行都要经过统一 RuntimeClient。

结论：先封装 RuntimeClient，再逐步迁移 5409 能力。

桌面端专家

一键启动

商用用户不应该手动开三个端口。桌面 App 要负责启动、健康检查、权限提醒、端口冲突处理。

结论：桌面端是进程管理器，不是另一个业务入口。

自动化执行专家

真实执行

5409 里有真实平台操作经验，不能直接丢弃。要把浏览器、账号、发布、互动、回读模块拆出来，迁入 Runtime。

结论：5409 终态必须消失为独立项目，只保留迁移后的 Runtime 能力。

安全与审计专家

不能假成功

发布、评论、私信不能只看 task completed。必须有发送动作、页面回读、截图/文本证据和失败原因。

结论：Runtime 返回统一 Evidence，不认裸 sent=true。

QA / 交付专家

验收

验收必须按业务链路，不按按钮可点击。重点是 4 条互动闭环、发布闭环、账号过期、worker 断开、权限缺失。

结论：每条链路必须有可复跑脚本和页面证据。

三、终极架构

KaypalAI 内容创作平台.app
  ├─ 打开唯一入口: http://127.0.0.1:3010
  ├─ 启动 Core API: 3011
  ├─ 启动 Local Runtime: 内部端口或进程 IPC
  └─ 负责健康检查、权限提醒、端口冲突、更新

3010 Web UI
  └─ 只调用 3011 /api

3011 Core API
  ├─ Auth / Kaypal 授权
  ├─ AccountProfileService
  ├─ Material / Topic / Article / Publishing
  ├─ Interaction Orchestrator
  ├─ RuntimeClient
  ├─ EvidenceService
  └─ AuditLogService

Kaypal Local Runtime
  ├─ BrowserControl
  ├─ AccountProfile
  ├─ PlatformPublisher
  ├─ InteractionExecutor
  ├─ ReadbackVerifier
  └─ EvidenceCapture
最终判断标准：用户只启动 KaypalAI 内容创作平台，只访问 3010；任何真实平台动作都由 3011 创建任务、Runtime 执行、3011 保存证据、3010 展示结果。

P3 废除 5409 独立前端和固定端口 删除 3010/3011 对 http://127.0.0.1:5409 的业务依赖； 5409 前端不再打包，不再作为用户或开发入口。 全仓搜索 5409/auto-upload 业务直连，只剩迁移说明或兼容测试。 2-3 天

五、第一轮具体改造清单

3010 前端

  • 删除或隐藏所有直接打开 http://127.0.0.1:5409 的入口。
  • 运行检查页改成“本地执行引擎”，不要显示技术端口作为主信息。
  • 发布中心、客户互动、账号设备全部只走 3011 API。
  • 失败状态统一展示：未启动、未登录、验证码、权限缺失、平台页面变化、回读失败。

3011 后端

  • 新增 backend/src/modules/runtime/。
  • 把 AutoUploadClient 包进 LocalRuntimeClient。
  • 所有执行返回统一 RuntimeExecutionResult。
  • 所有证据保存到统一 EvidenceService，不让前端猜成功。

5409 / auto-upload

  • 按模块迁移，不保留独立产品形态。
  • 把 main.py 中的平台 API 拆成 Runtime handlers。
  • 把 cdp_runtime.py、platform_douyin_cdp.py、platform_channel_cdp.py 迁入 Runtime。
  • 迁移完成后移除 5409 固定端口和自带前端。

Desktop

  • 启动时检查 3010/3011/Runtime 是否占用，冲突则自动换端口或提示。
  • 写 runtime-manifest.json 给 3010/3011 读取。
  • 首次启动引导 macOS 辅助功能、自动化、文件访问权限。
  • 打包时把 Runtime 作为内部资源，不依赖用户本机路径。

六、统一数据契约

type RuntimeExecutionResult = {
  ok: boolean;
  status: 'success' | 'failed' | 'blocked' | 'skipped';
  reasonCode:
    | 'runtime_unavailable'
    | 'account_not_logged_in'
    | 'captcha_required'
    | 'permission_missing'
    | 'target_not_found'
    | 'send_failed'
    | 'readback_failed'
    | 'platform_changed'
    | 'success';
  userMessage: string;
  technicalMessage?: string;
  runtime: {
    mode: 'local-runtime' | 'auto-upload-worker';
    version?: string;
    engineUrl?: string;
    profileDir?: string;
    cdpPort?: number;
  };
  evidence: Array<{
    type: 'screenshot' | 'text' | 'page-url' | 'network' | 'readback';
    label: string;
    value?: string;
    path?: string;
    createdAt: string;
  }>;
  readback?: {
    expectedText?: string;
    actualText?: string;
    matched: boolean;
  };
};
关键规则：前端不能因为 completed 显示回读成功；后端不能因为 sent=true 判定真实成功。 必须看 Runtime 证据和 readback。

七、不能做的事

  • 不能现在直接删除 5409。它里面有已经跑通过的平台执行经验，删了会倒退。
  • 不能让 3010 前端直接调 5409。这样会形成第二套入口和第二套状态。
  • 不能把 5409 整个 Python 项目原封不动塞进 3011。3011 会变成不可维护的混合执行层。
  • 不能只做 UI 隐藏，不做错误码和证据统一。否则商用时还是会假成功。

八、验收标准

验收项 通过标准
单入口 用户只打开 3010；页面上没有 5409 作为独立产品入口。
启动 桌面 App 一键启动 3010、3011、Runtime；失败能显示具体原因。
客户互动 抖音评论、抖音私信、视频号评论、视频号私信各连续 5 轮真实读、生成、发送、回读。
发布中心 图文和视频发布有真实上传、发布、平台结果或页面回读。
失败处理 5409/Runtime 断开、账号过期、验证码、权限缺失、目标为空、回读失败都不能显示成功。
证据 每个真实执行任务都有日志、截图或文本证据，可在 3010 查看。
