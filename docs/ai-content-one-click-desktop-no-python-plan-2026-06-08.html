一体化桌面安装包方案：去 Python / 去 Docker / Node Playwright Runtime

目标不是把 Node、Python、Postgres、Redis、Chrome 换一种方式让用户安装，而是把这些运行时收进应用内部或彻底替换掉。 小白用户只需要下载安装一个 KaypalAI 桌面应用，登录 Kaypal 账号后即可使用平台账号、AI 执行和自动化能力。

决策：不做 PyInstaller / Nuitka 短期方案 主线：Electron + Node + Playwright 本地数据：SQLite 浏览器：内置 Chromium 云端：Kaypal 授权 / 订阅 / 积分
用户需要手动安装的技术依赖 0 个 不要求 Node、Python、Docker、Postgres、Redis、Chrome。
产品主链路运行时 1 个 App Electron 主进程统一拉起本地后端、任务引擎和浏览器控制。
迁移原则 接口兼容 先兼容现有 3010/3011 接口，再替换内部实现。

结论

不要走“短期打包 Python sidecar”的路线。正式产品路线直接把 Agent-S / Python sidecar 能力迁到 Node/Playwright。

安装包交付形态改成：Electron 壳 + 内置 Node 后端 + SQLite 本地库 + Node Agent Runtime + 内置 Playwright Chromium。Kaypal 账号、订阅套餐、积分余额继续走测试站/正式站云端接口，本机只保存设备授权、平台登录态、任务记录和证据文件。

为什么不能继续让用户装一堆依赖

小白用户安装成本太高

Node、Python、Docker、Postgres、Redis、Chrome 每一个都可能遇到权限、路径、服务启动、杀毒软件、端口冲突问题。用户看到的是“软件装不上”，不是“依赖没配好”。

售后成本不可控

一旦依赖安装失败，排查点会散落在系统服务、环境变量、Docker 状态、浏览器路径和 Python 包版本里。这个模型适合开发机，不适合面向普通用户分发。

自动化执行需要稳定边界

平台登录态、CDP profile、证据截图、任务队列都需要固定目录和固定生命周期。让用户机器上的外部 Chrome / Docker / Python 参与主链路，会放大不可复现问题。

Python sidecar 只是把问题藏起来

PyInstaller / Nuitka 能减少用户安装 Python，但仍然保留 Python 运行时、Python 依赖、跨平台构建和调试链路。既然目标是小白安装包，就不把它作为产品主线。

Node Agent Runtime 设计

模块拆分

  • SessionStore：任务会话、运行状态、暂停/取消、审批状态。
  • TaskRunner：执行队列、重试、超时、失败归因。
  • BrowserController：Playwright Chromium、CDP profile、页面复用、cookies/storage state。
  • EvidenceStore：截图、HTML 快照、网络证据、执行日志索引。
  • ApprovalGate：真实发布、真实回复前的确认闸口。
  • PlatformAdapters：抖音、快手、小红书、视频号各自的读/发流程。
  • EventStream：前端实时显示执行进度、二维码、错误和证据。

优先兼容的 API

  • POST /api/agent-s/sessions：创建执行会话。
  • POST /api/agent-s/sessions/:id/run：启动任务。
  • GET /api/agent-s/sessions/:id/events：拉取/订阅执行事件。
  • POST /api/agent-s/sessions/:id/cancel：取消任务。
  • POST /api/agent-s/sessions/:id/approve：用户确认。
  • GET /api/agent-s/sessions/:id/artifacts：证据文件列表。

关键原则

不要先大改前端。第一阶段先让 3010 仍然调用熟悉的本地接口，只把接口背后的 Python sidecar 换成 Node runtime。等执行链路稳定后，再统一前端状态字段和证据展示。

本地数据方案

放在 SQLite 的数据

  • 任务、执行记录、失败原因、重试状态。
  • 证据文件索引、截图路径、页面探测结果。
  • 平台账号元数据：平台、昵称、状态、profile 路径。
  • 本机设备授权、能力开关、最近心跳。
  • 本地队列和待确认记录。

不放在 SQLite 的数据

  • Kaypal 主账号密码：不在本机保存。
  • 订阅等级、积分余额：以 Kaypal 云端为准，本地只缓存显示。
  • 平台浏览器 profile：继续用文件目录保存，由 Playwright 持久上下文管理。
  • 大体积证据文件：落盘到 evidence/，数据库只存索引。

安装包体验

  1. 用户下载安装 KaypalAI 桌面应用。
  2. 首次启动时，App 自动创建应用数据目录、SQLite 数据库、日志目录、证据目录和浏览器 profile 根目录。
  3. Electron 主进程拉起内置后端和 Node Agent Runtime，检查内置 Playwright Chromium 是否可用。
  4. 用户用 Kaypal 账号登录，系统调用 Kaypal 云端获取账号、订阅、积分和设备授权。
  5. 用户绑定抖音、快手、小红书、视频号时，系统打开内置 Chromium 持久浏览器，扫码登录后保存 profile/cookies/storage state。
  6. AI 执行任务消耗积分，执行结果、证据和失败原因写入本地，同时关键消耗回传 Kaypal 云端。

迁移阶段

Phase 0

冻结现状与备份

固定当前可运行版本、数据库备份、依赖清单、端口和 sidecar 状态。后续迁移失败可以回退。

已完成/半天
Phase 1

Node Runtime API 兼容层

新建 Node Agent Runtime 骨架，先实现 Agent-S 关键 API 的兼容返回、事件流、证据字段和错误结构。

2-3 天
Phase 2

Postgres / Redis 迁到 SQLite

抽出存储适配层，把本地任务、队列、证据、平台账号状态迁到 SQLite；保留云端授权和积分接口。

3-5 天
Phase 3

Playwright Chromium 与 CDP profile

实现内置 Chromium 启动、窗口复用、页面复用、cookies/storage state、二维码登录状态探测和证据截图。

4-6 天
Phase 4

平台适配器迁移

按平台迁移抖音评论/私信、视频号评论/私信、快手、小红书读写流程。每个动作必须有页面探测、发送后验证和证据落库。

5-8 天
Phase 5

Electron 打包与启动编排

把前端、后端、SQLite schema、Node Runtime、Playwright Chromium 和 native runtime 依赖收进安装包，主进程统一管理生命周期；重点补齐 sharp 等 native optional dependency 的资源检查。

3-5 天
Phase 6

安装器、自动更新、干净机器验收

在没有 Node/Python/Docker/Postgres/Redis/Chrome 的干净机器上验收安装、登录、绑定平台、执行任务、重启恢复和卸载。

3-5 天

排期判断

快速可演示版本：7-10 天。可给普通用户安装的生产版本：建议按 3-5 周规划，至少 2-3 名工程师并行推进。

验收标准

验收项 通过标准
干净机器安装 机器没有 Node、Python、Docker、Postgres、Redis、Chrome，安装后 App 可直接启动。
Kaypal 授权 登录后能从 Kaypal 云端读取账号、订阅等级、积分余额、设备授权状态。
本地数据库 任务、账号状态、证据索引落到 SQLite；退出重启后不丢。
平台登录 抖音、快手、小红书、视频号能通过内置 Chromium 持久 profile 登录；账号页能准确刷新状态。
互动执行 抖音评论/私信、视频号评论/私信读写流程能执行，有发送后验证和证据截图。
积分消耗 用户调用 AI 执行任务时，按规则消耗积分；失败、取消、未执行不误扣。
故障恢复 浏览器崩溃、页面卡住、网络失败时，系统给出可读错误、保留证据，并允许重试。
卸载 卸载主程序时不残留服务；用户数据目录可选择保留或清理。

风险和处理方式

现有代码可能硬绑定 Postgres / Redis

处理：先做存储适配层，不直接在业务代码里到处改 SQL。迁移期间保留开发环境 Postgres，产品包走 SQLite。

平台网页自动化会变

处理：平台适配器必须返回探测证据、截图和失败归因。不能再只靠 selector 猜测，要把 5409 已验证的页面探测语义迁成 Node 实现。

内置 Chromium 可能和平台检测冲突

处理：使用真实可见窗口、持久 profile、稳定 user data dir；系统 Chrome 只作为调试 fallback，不作为用户主链路。

SQLite 并发能力弱于 Postgres

处理：桌面端是单用户本地进程，使用 WAL、串行任务队列、短事务即可满足；云端协同数据不放本地 SQLite 做最终事实。

明确不做

  • 不做 PyInstaller / Nuitka 作为正式产品主线。
  • 不做 随 App 携带 Python runtime 和 Python site-packages。
  • 不做 要求用户安装 Docker Desktop。
  • 不做 在用户机器安装 Postgres / Redis 系统服务。
  • 不做 要求用户安装系统 Chrome 才能跑主流程。
  • 不做 在本地保存 Kaypal 主账号密码。

下一步实施清单

  1. 列出当前 3011 后端所有依赖 Postgres / Redis / Agent-S 的接口和调用点。
  2. 定义 LocalRuntimeStorage 接口，先让任务、证据、平台账号状态能从 SQLite 读写。
  3. 新建 desktop/runtime 或 backend/src/modules/local-runtime，实现 Node Agent Runtime API 兼容层。
  4. 把 Playwright Chromium 下载和路径固定到 Electron resources，启动时做 runtime self-check。
  5. 优先迁平台账号登录状态识别和 openEntry，因为这是所有评论/私信读写的前置条件。
  6. 再迁抖音评论/私信、视频号评论/私信，每个动作都要求证据截图和发送后验证。
  7. Phase 5 必须补安装包 native 依赖检查：至少覆盖 sharp 及其平台包、Playwright runtime 包、Prisma native engine，避免后端 bundle 在干净机器启动时报缺模块。
  8. 最后做安装包验收：干净 Windows / macOS 用户环境，不装任何开发依赖。
