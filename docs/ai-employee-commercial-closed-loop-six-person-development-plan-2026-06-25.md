# 3010 AI 员工 OS 商用闭环优化开发文档

## 1. 背景

3010 当前已经具备自动获客、抖音评论、抖音私信、微信任务、视频号回复、发布中心、平台账号、操作证据等模块。和本地炼刀 1.8.5 对比后，3010 的功能覆盖面已经接近，但商业闭环还不够集中：任务能跑，证据能留，但客户线索沉淀、统一调度、运营复盘和交付验收还没有完全产品化。

本次优化目标不是继续横向堆功能，而是把 3010 收口成一个可销售、可交付、可复盘的获客与私域运营系统。

## 2. 总目标

把 3010 做成三条闭环：

1. 获客闭环：搜索视频和评论 -> 自动触达 -> 生成客户线索 -> 后续跟进。
2. 任务闭环：创建配置 -> 后台定时执行 -> 失败恢复 -> 留证据 -> 可导出。
3. 运营闭环：今日跑了什么 -> 触达了谁 -> 谁有意向 -> 下一步跟进谁。

## 3. 对标结论

### 3.1 对标炼刀

炼刀强在任务型运营闭环：

- 页面密度高，配置、记录、证据、执行按钮集中。
- 自动获客配置包含搜索关键词、评论匹配关键词、评论内容、每日上限、启动时间、跳过重复、黑名单。
- 记录表直接展示候选评论、评论回复、覆盖视频、状态、结果和证据。
- 微信体系围绕联系人、群发、加好友、朋友圈发布、朋友圈营销拆任务，并且要求本地执行器真实接管。

3010 已经追上的部分：

- 自动获客有配置、记录、证据、每日上限、启动时间、跳过重复。
- 后端已有定时执行、启动恢复、持久化、去重、多视频分散和无关键词命中时视频直评兜底。
- 微信任务已有联系人同步、群发、加好友、朋友圈发布、朋友圈营销、证据和计划列表。

3010 还差的部分：

- 自动获客结果没有统一进入客户线索池。
- 证据弹层和记录详情还不够统一。
- 配置和记录仍有部分 JSON 文件持久化，应该逐步迁到数据库。
- 各模块状态和操作模型不够统一，用户需要理解太多底层概念。

### 3.2 对标主流产品

主流产品强在三件事：

- CRM 客户资产：线索、客户、标签、来源、生命周期、跟进状态、转化归因。
- Workflow 自动化：触发条件、动作、分支、限频、重试、失败处理、权限、审计。
- 运营分析：触达量、成功率、失败原因、线索质量、渠道 ROI、团队协作。

3010 当前更像“自动化执行平台”，下一步要补成“获客 CRM + 自动化任务 + 本地执行器”的组合。

### 3.3 GitHub 开源项目参考结论

调研结论：没有一个 GitHub 项目可以整套直接抄成 3010。可用策略是拆模块借鉴：CRM 客户资产参考 CRM 项目，社媒调度参考社媒管理项目，评论触发自动化参考 Manychat 类项目，微信/抖音执行器继续保留 3010 自研本地控制链路。

| 项目 | 许可证/风险 | 可借鉴内容 | 是否建议直接复制代码 |
|---|---|---|---|
| `gitroomhq/postiz-app` | AGPL-3.0，闭源商用直接复制风险高 | 社媒账号、内容发布、任务调度、队列、发布记录 | 不建议直接复制，只参考架构和交互 |
| `espocrm/espocrm` | AGPL-3.0，闭源商用直接复制风险高 | Lead、Contact、Activity、Timeline、权限、跟进状态 | 不建议直接复制，只参考 CRM 模型 |
| `twentyhq/twenty` | GPL/AGPL/企业授权混合，需谨慎 | 现代 CRM UI、对象模型、客户详情、时间线 | 不建议直接复制，只参考产品设计 |
| `wechaty/wechaty` | Apache-2.0，许可友好 | 微信联系人、会话、消息事件、Bot/RPA 抽象 | 可研究接口抽象，但 Windows 微信控制仍走自研执行器 |
| `ayuuxh2/insta-p8` | MIT，许可友好但项目规模小 | 评论触发自动化、AI 回复、私信/评论线索捕获 | 可重点拆表结构、API 和页面思路，复制前需代码审查 |
| `mashukui/douyin_one_spider` | MIT，许可友好但稳定性需实测 | 抖音搜索、评论采集、GUI 工具思路 | 可参考采集字段和入口，不建议依赖其执行链路 |
| `openscrm/dashboard` | Apache-2.0，但只是后台前端局部 | 企业微信 SCRM 后台页面结构 | 可参考前端信息架构 |

推荐采用“三个参考源”：

1. `ayuuxh2/insta-p8`：参考评论触发、自动回复、线索捕获的业务闭环。
2. `gitroomhq/postiz-app`：参考社媒账号、任务、调度、发布记录和失败重试。
3. `espocrm/espocrm` 或 `twentyhq/twenty`：参考客户线索池、客户详情、标签、时间线和跟进状态。

不能直接抄的部分：

- 不直接把 AGPL 项目代码拷进 3010，避免闭源商用合规风险。
- 不直接依赖抖音采集脚本作为核心执行器，避免页面变化和风控导致商用不稳定。
- 不用第三方项目替换 3010 当前本地执行器。抖音评论、微信通讯录、微信任务、证据截图仍由 3010 自研执行器负责。

可以直接吸收的部分：

- CRM 数据模型。
- 线索详情页结构。
- 时间线和活动记录。
- 社媒账号和任务队列结构。
- 评论触发自动化的规则配置。
- 自动化记录详情弹层。
- 失败原因聚合和重试状态。

### 3.4 本地 Kaypal Closer 项目评估与 CRM 插件化结论

本地项目 `/Users/yanghy/Projects/kaypal-closer` 不建议整体并入 3010。它是从 OpenCowork 分叉出来的 Electron 桌面 App，包含 `main / preload / renderer`、IPC、本地 SQLite、桌面沙盒、安装包构建、多模型 Agent、Skills、远程控制等完整桌面应用能力。3010 当前主线是 Web 后台 + 本地执行器 + 自动获客/微信任务，直接整包合并会引入两套架构、两套权限、两套任务和两套运行时。

但它里面的 CRM 和商用化底座很适合抽出来做成 3010 的独立付费应用：在应用市场里展示、购买、安装，安装后左侧导航才出现 CRM。这样既能补客户管理能力，又不会把主系统默认页面继续变复杂。

CRM 应用市场逻辑：

1. 用户进入应用市场。
2. 看到“CRM 客户管理”应用。
3. 未购买时展示介绍、价格、试用/购买按钮。
4. 购买后展示“安装”按钮。
5. 安装后左侧导航出现“CRM 客户管理”。
6. 卸载后导航隐藏，客户数据保留为归档状态，不直接物理删除。
7. 后端所有 CRM API 必须校验购买状态、安装状态和当前用户权限，不能只靠前端隐藏入口。

建议抽进 CRM 应用的部分：

- CRM 基础模型：客户、公司、联系人、商机、跟进记录、任务、备注、时间线。
- 数据导入 dry-run：CSV/XLSX 解析、字段识别、字段映射建议、邮箱/手机号校验、PII 标记、只预览不直接入正式客户表。
- 审计和证据链：操作记录、执行结果、失败原因、商用测试证据导出、后台任务证据链。
- Secret Vault 思路：平台 token / CRM token 本地加密、主进程解密、前端不碰明文、token 轮换/吊销/隔离状态。
- CRM Connector 设计：HubSpot / Salesforce / Twenty / 飞书字段映射、只读沙盒接入、canary 限量读取、映射到本地 CRM 表。
- 商用化安全闸门：dry-run、审核、小批量 canary、回滚方案、kill switch、执行前后验证。
- 本地商业化测试框架：证明没有乱写表、没有外发、数据隔离和权限正确。

不建议抽进 3010 的部分：

- Electron 桌面壳、IPC 桥、托盘、菜单、窗口系统。
- OpenCowork 原始聊天 Agent、多模型配置、会话系统、文件读写助手。
- WSL/Lima 沙盒和命令执行隔离。
- PPTX/DOCX/PDF/XLSX Skills 文档生成系统。
- Feishu/Slack 远程控制、webhook 控制、ngrok/tunnel。
- NES/DNA/KPI/Commercial Demo 这类概念展示页面。
- 大量 contract-only 页面。可以抽规则和测试，不抽 UI。
- Kaypal Cloud Runtime 的 desktop runs、stream、evidence back to cloud 架构。
- 整套组织、订阅、权限系统原样搬运。可以参考字段，但要接 3010 现有账号、余额、权限体系。

CRM 第一版定位：

- 不做复杂企业 CRM。
- 不做 HubSpot/Salesforce 真实双向同步。
- 不做复杂销售漏斗和 KPI 概念页。
- 只做“本地 CRM + 客户线索承接 + 自动获客结果沉淀”。

推荐业务闭环：

自动获客 / 微信任务 / 视频号任务 -> 产生线索 -> 进入 CRM 应用 -> 分配跟进人 -> 生成跟进任务 -> 留证据 -> 成交或无效归档。

## 4. 本次开发范围

### 4.1 必做

- 自动获客结果进入客户线索池。
- 新增客户线索列表和客户详情。
- 自动获客配置、记录、去重、执行统计迁移到数据库。
- 统一任务记录详情弹层和证据弹层。
- 统一任务状态、失败原因、重试、暂停、恢复、删除。
- 后台定时任务页面关闭后继续执行。
- 商用验收脚本覆盖自动获客、微信任务和证据导出。
- 应用市场新增“CRM 客户管理”付费应用，支持购买、安装、卸载、权限校验。
- CRM 安装后承接自动获客线索，未安装时自动获客仍能运行，但只保留任务记录和基础线索摘要。

### 4.2 暂不做

- 不新增新的平台渠道。
- 不重做整个 UI 设计系统。
- 不把 CRM 做成默认内置页面。
- 不做复杂 CRM 销售漏斗。
- 不做 CRM 真实双向同步。
- 不把 Kaypal Closer 整体并入 3010。
- 不做无边界批量触达，所有自动执行必须保留限频、黑名单、风控阻断和证据。

- 每天开工前检查主干状态、未完成任务、阻塞点。
- 给 6 个方向拆任务，按接口契约并行推进。
- 每天收一次集成，统一解决 API、状态、文案、证据格式冲突。
- 所有 PR 以“真实商用闭环”为验收，不接受只做页面或只写假记录。
- 每个阶段结束后出一份验收结论和剩余风险。

负责人：

- 数据与运营分析工程师协作。

- 保存触达状态：待触达、已触达、失败、有意向、待跟进、无效。

### Phase 2：自动获客商用闭环

周期：4 天

负责人：

抖音自动化任务：

- 评论区有匹配关键词时回复评论。

## 7. 数据模型草案

### 7.1 Lead

客户线索主表。

字段建议：

## 11. 任务拆分原则

每个任务单必须写清楚：

- 改哪个页面或接口。
- 输入是什么。
- 输出是什么。
- 真实执行怎么验收。
- 证据在哪里看。

不接受以下交付：

- 只有页面，没有真实 API。
- 只有任务记录，没有真实执行。
- 只有截图，没有动作结果。
- 失败原因是技术黑话，用户看不懂。

## 12. 风险和处理

| 风险 | 影响 | 处理方式 |
|---|---|---|
| 抖音页面结构变化 | 搜索、评论、发送失败 | 保留选择器版本、截图诊断、失败原因、热修配置 |
| 微信版本差异 | 联系人同步、发送、朋友圈失败 | 固定支持版本范围，环境检查提前阻断 |
| 平台风控 | 评论/私信/群发失败 | 默认限频、每日上限、黑名单、连续失败自动停用 |
| 数据迁移出错 | 历史配置和记录丢失 | 先读旧 JSON，再写 DB，保留迁移备份 |
| UI 继续变复杂 | 用户不会用 | 所有运营页面按炼刀密度收口，少解释，多表格 |
| 验收只停在假数据 | 商用不可交付 | QA 必须用真实账号、真实页面、真实证据验收 |
