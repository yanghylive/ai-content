## 3. 必须整改的问题

### P1-A：重建发布包，不能继续复用 1.1.105

**问题**：P1-2 的 `getAccounts()` 修复、悬浮球拖拽修复和 preload 打包修复都晚于现有 `1.1.105.exe` 构建；现有包同时缺账号同步修复和悬浮球 bridge。最新提交 `7d251a64` 已将悬浮球默认改为关闭，这能避免新用户默认触发坏 bridge，但托盘/config 仍允许 `hoverBallEnabled=true`，而且 P1-2 账号同步修复仍未进入包，因此不能用“默认关闭”替代重建包验收。

**方案**：按已记录的版本决策升至 `1.1.106`，在同一提交上重新生成 `backend/dist-bundle-sqlite`，再构建 Windows 和 macOS 包。不要覆盖已发布的 `1.1.105`，除非发布负责人明确确认该版本尚未对外使用。

**验收**：

1. 从新包解包确认 `preload-hoverball.js` 存在。
2. 从新包解包确认 backend `getAccounts()` 在普通列表路径调用 `syncLocalEngineAccounts`。
3. 运行 `check-package-contents --win-only` 和 `check-full-installer-assets --installer=<新 exe>`。
4. 在新包启动的 3010/3011 上跑 Agent-S health/status、真实读页面和草稿任务，并导出 evidence。
5. 用新版本 metadata、Win/Mac 包 hash 做远端双通道验证。

### P1-B：门禁不能只保留 `tail` 输出

`scripts/pre-release-full.mjs` 多处用 `2>&1 | tail -N`（包括 [L4](/Users/yanghy/Documents/New%20project/ai-content/scripts/pre-release-full.mjs:140)）。`pipefail` 能让失败码继续向上传递，但不会保存被截掉的原始错误；本次 L4 汇总只显示“Command failed”，根因必须另跑精确命令才能看到。这不满足附件清单要求的“保留完整日志，不能用截断输出判绿”。

**方案**：每个 step 写入带时间和 commit 的证据文件，使用 `tee` 仅做屏幕摘要；汇总同时记录命令、退出码和完整日志路径。失败时禁止只上传 `tail` 片段。

### P2-B：修复精确解包检查的临时目录泄漏

[check-full-installer-assets.js](/Users/yanghy/Documents/New%20project/ai-content/desktop/scripts/check-full-installer-assets.js:54) 成功解包后直接返回临时目录；成功、断言失败和后续异常路径都没有统一 `rmSync`。本次复跑后在 macOS `os.tmpdir()` 下观察到 7 个 `cfa-installer-*` 目录，说明每次 7z 解包都会在系统临时目录留下完整安装包内容。

**方案**：保存 extraction temp root，在主检查函数外围使用 `try/finally` 清理；清理失败只记录 warning，不覆盖原始失败码。补一次成功、断言失败、7z 失败三种路径的测试。

### P2-C：补自愈 stderr flush 时序测试

[main.js](/Users/yanghy/Documents/New%20project/ai-content/desktop/main.js:1606) 在 `backendStdout.end()` / `backendStderr.end()` 后立即调用 `tailFileSync()`。写流尚未完成 flush 时，最新的 `P2010` 可能读不到，导致应自愈而未自愈。

**方案**：将 close 处理改为等待两个写流的 `finish`（或在 data/close 设计中使用已确认落盘的缓冲），再读取本次启动 offset 之后的日志。测试必须覆盖：大于 4KB stderr、日志追加跨启动、WAL/SHM rename 失败、自愈失败后的重试上限。sidecar rename 失败时必须明确返回阻断状态，不能让外层把重建当作完整成功。

同一处还有两个清库误判风险必须一并修复：

- [main.js:1667](/Users/yanghy/Documents/New%20project/ai-content/desktop/main.js:1667) 将 Prisma code `14`（`SQLITE_CANTOPEN`，常见原因是权限/路径不可用）列入损坏信号；它不等于数据库损坏。
- `P2010[\\s\\S]{0,400}database` 过于宽泛，普通 raw query 错误或 `database is locked` 也可能命中。
- [main.js:1617](/Users/yanghy/Documents/New%20project/ai-content/desktop/main.js:1617) 在 `isQuitting` 判断之前执行上报和自愈；应用退出导致子进程以 signal 关闭时 `code` 通常为 `null`，`null !== 0` 会进入该分支。

**方案补充**：只允许明确的 `database disk image is malformed`、`file is not a database`、`SQLITE_CORRUPT` 或明确的 `SQLITE_NOTADB` 触发自愈；把 `isQuitting` 提前到 close 处理器的上报/自愈之前。加入 CANTOPEN、locked、正常 SIGTERM 退出均不改名不清库的回归测试。

### P2-D：决定 Cloud API 遗留范围

桌面端 [cloud-api.js](/Users/yanghy/Documents/New%20project/ai-content/desktop/cloud-api.js:213) 和前端 adapter 仍有 `/api/v1/auth/login`、`/api/v1/usage/stats`、`/api/v1/subscription` 调用；`cloud-api-server/server.js` 只实现老的内容/去重接口，且生产未配置 `API_KEY` 时这些接口返回 503。

- 若移出范围：删除或隐藏这些调用、补回归测试，并在清单明确“遗留禁用”。
- 若保留：实现完整路由和统一鉴权；不能把共享 `API_KEY` 放入安装包。

### P2-E：自动更新的“跳过版本”目前仍会下载

`desktop/auto-updater.js:64-69` 在收到 `update-available` 时发现跳过版本会直接返回，但本地 `electron-updater` 的 `AppUpdater.doCheckForUpdates()` 会在发出该事件后继续执行 `autoDownload ? downloadUpdate(...)`（`desktop/node_modules/electron-updater/out/AppUpdater.js:413-423`）。因此 `skipUpdate()` 只隐藏界面，不能阻止下载；同时 `autoInstallOnAppQuit=true` 还可能在用户退出时安装被跳过的版本。

**方案**：将自动下载改为显式下载（`autoDownload=false`），仅在确认版本未被跳过时调用 `downloadUpdate()`；或在检查前过滤跳过版本。补测试覆盖“跳过版本不产生下载请求”“手动下载仍可用”“下载完成后安装必须明确确认”。在产品确认前，不应把“安装仍由用户触发”作为已证明结论。

### P2-F：错误上报接口的 HTTP 204 不是落 OSS 证据

`cloud-api-server/server.js:251-257` 在 OSS 写入失败时也返回 `204`，这是为了让客户端静默失败，但会让“HTTP 成功”与“云端确实保存”无法区分。验收不能只记录 `204`，必须在 OSS 读取到对应 `error-reports/<date>/<uuid>.json`；否则只能标记为未证明。

**方案**：保留客户端静默策略，同时在发布验收中用唯一 `reportId/kind` 做 OSS readback；服务端日志和监控需要单独暴露 OSS 写入失败计数。
