# 运行时可靠性对比矩阵

日期：2026-08-05  
方法：运行时可靠性法  
用途：判断系统能否在真实环境持续运行，而不是只判断功能是否存在。

## 运行时模型

JIUZHANG 当前可以抽象为：

`前端/PWA -> 云端 API -> 本地 Bridge/桌面端 -> 平台账号运行时 -> 外部平台结果 -> 结果回读/审计`

参考产品静态材料显示其更偏向：

`Windows 桌面端 -> 内嵌本地服务/Python/Playwright/SQLite -> 微信/社交平台 -> 本地任务结果`

这只是拓扑差异，不代表任何一方天然更稳定。稳定性必须按下面的故障场景验证。

## 故障矩阵

| 故障/风险 | 参考产品观察 | JIUZHANG 当前证据 | 商用要求 | 判定 |
|---|---|---|---|---|
| 本地服务启动慢或退出 | 本地服务与桌面端强绑定 | 3011 启动超时曾是 Windows 真机问题；v1.1.60 已加入密钥和诊断修复 | 等待、限次重试、日志路径和用户动作必须一致 | 待 Windows A 证据 |
| 本地凭据不可用 | 本地运行时保存账号/配置 | 已改用 Electron safeStorage/设备密钥方向 | 首次安装、升级、权限变化都不能导致静默失败 | B，待 A |
| 平台登录过期 | 本地任务可直接感知登录态 | 有 `ready/needs_login/blocked/stopped` 等状态，需统一前端显示和任务迁移 | 任何过期都不得显示成功；任务进入 `needs_login` | 部分完成 |
| 账号绑定状态不一致 | 本地账号运行时是主要状态源 | 视频号出现弹窗与列表不一致；账号、页面、发布器状态源需统一 | 同一账号 ID、平台、登录态、刷新时间可追踪 | P0 缺口 |
| 云端额度冻结 | 本地任务可被本地能力控制 | 云端额度/冻结需要与执行授权联动 | 冻结时不得启动外部副作用，文案需可行动 | 待生产验证 |
| 网络中断 | 本地服务可能继续运行 | 云端 API、Bridge、平台之间存在断点 | 保留任务、幂等键和恢复策略 | 待验证 |
| 平台风控/拒绝 | 需按平台错误停止或换人工 | 现有状态和错误模型存在，但真实平台错误分类未完整闭环 | 不盲目重试，展示平台原因和下一步 | 待真实平台验证 |
| 重复点击/重复重试 | 本地任务系统需防止重复外部动作 | 需要核对 publish intent、任务 ID 和执行器幂等 | 同一业务意图只能产生一个外部副作用 | P0 缺口 |
| 进程崩溃后恢复 | 本地 SQLite/任务服务有恢复基础 | 交接记录指出 durable worker 和真实 Electron E2E 仍不足 | 重启后可恢复、可取消或明确失败 | P0 缺口 |
| 协同取消 | 需让 UI、云端、本地执行器一致停止 | 交接记录明确 collaborative cancel 未完成 | 取消必须有最终态，不得出现 UI 已取消但平台仍发出 | P0 缺口 |
| 微信桌面检测 | 参考产品内置桌面运行时 | JIUZHANG 仅 macOS 检测；非 macOS 明确返回不支持 | Windows 不得显示可执行微信自动化入口 | 明确平台缺口 |
| 微信目标定位错误 | 本地桌面自动化最容易产生误发 | JIUZHANG 有窗口、截图、搜索回读和人工确认设计 | 目标不唯一或未回读确认时必须阻断发送 | 部分完成 |
| 多租户串数据 | 参考产品偏本地单用户 | JIUZHANG 有租户/成员/权限基础 | 每次查询、任务、账号、证据都必须带租户边界 | 待专项回归 |
| 账号删除/解绑 | 本地 profile 和任务引用需清理 | 有账号删除入口，需确认任务/凭据/历史关联策略 | 解绑后禁止新执行，历史按策略保留 | 待验证 |
| 备份恢复 | 本地数据库和 profile 均是状态 | 仍需演练 SQLite、本地 profile、云端数据恢复 | 恢复后账号、任务、审计可关联且不重复执行 | P1 缺口 |
| 更新失败/回滚 | 本地应用需可回退 | OSS feed/安装包已存在，签名和回滚制度仍需补 | 失败可恢复，旧版本可启动，数据不损坏 | P0/P1 |
| 观测与诊断 | 本地日志通常更集中 | 已有 backend launch/stdout/stderr 等诊断方向 | 一次问题能关联版本、设备、租户、账号和任务 ID | 部分完成 |
| 56 条 lint 警告 | 静态警告不代表运行时失败 | 需要按风险而非一次性清零 | 先消除状态机、异步、未处理错误相关警告 | P1 |

## 可靠性指标

实现前先确定指标，避免只看“页面能打开”：

| 指标 | 目标 |
|---|---|
| 假成功率 | 0；本地成功但平台失败不能被标记成功 |
| 重复外部副作用 | 0；同一 publish/interaction intent 不得重复执行 |
| 启动成功率 | 干净 Windows 环境连续安装启动通过 |
| 可恢复任务比例 | 可恢复故障都能恢复或转为明确失败 |
| 证据完整率 | 每个外部动作都有任务 ID、账号、时间、结果和日志关联 |
| 登录失效识别 | 登录失效不得继续执行，不得显示假绿 |
| 多租户隔离 | 交叉访问、任务、账号、文件和审计全部拒绝 |
| 发布后回读 | 外部链接/平台作品 ID 可回读或明确标为待确认 |
| 长时间运行 | 至少完成一轮 24 小时低频任务耐久性观察后再扩量 |

## 运行时优先级

### 第一优先级：统一状态源

账号状态、发布任务状态、互动任务状态、额度冻结状态必须定义唯一来源和迁移规则。前端轮询结果、桌面运行时结果和云端任务结果不能各自维护一套“成功”。

### 第二优先级：副作用幂等

发布、评论、私信、加好友和群发都属于外部副作用。任务必须有业务幂等键、执行锁、超时后的查询回读和不可重试错误分类。

### 第三优先级：可恢复执行

把一次性长调用拆成可持久化的执行单元，记录阶段、输入摘要、账号、权限、重试次数和证据。应用重启后要么继续，要么进入明确的人工确认态。

### 第四优先级：真实平台证据

所有真实发布和互动的最终判定必须来自平台回读、截图或可核验的外部记录，不能只依据本地进程退出码。

## 与参考产品的策略差异

| 方向 | 不采用的做法 | JIUZHANG 应采用的做法 |
|---|---|---|
| 本地执行 | 不直接复制对方的内嵌服务、脚本和资源 | 设计自有 Bridge/桌面执行器协议，保留审计和权限边界 |
| 能力扩张 | 不因对方有入口就全部开放 | 按真实用户任务和合规风险分级开放 |
| 稳定性 | 不把本地单机可运行当成商业可用 | 用状态机、幂等、回读、恢复和证据建立商业门槛 |
| 微信能力 | 不在 Windows 尚未支持时伪装成已支持 | 明确平台差异；先完成可控、可审计的最小闭环 |
| 发布 | 不只追求更多平台适配器 | 先把少数核心平台的真实发布回读做成稳定闭环 |

## 结论

当前最大工程差距不是“缺多少页面”，而是：

1. 外部动作的真实回读和假成功防护。
2. 账号状态、额度状态和执行权限的一致性。
3. 进程重启、网络中断、取消和重试的可恢复语义。
4. Windows 本地运行时与真实账号的长期稳定性。
5. 微信和社交互动能力在不同操作系统上的明确边界。

在上述问题没有形成 A 级证据前，不进入大规模能力扩张，也不把参考产品的静态功能列表当作 JIUZHANG 的商用承诺。
