> 审计日期：2026-09-05
> 方法：逐文件读源码坐实（非摘要推断），每条问题带 file:line 证据
> 结论先行：自动获客不是「一处有问题」，而是**三套并行系统各自都埋着硬伤**，从「假数据返回」「伪自动」「证据门禁自相矛盾」到「审计边界分裂」「内存态风险控制」，加起来是**十几个可落地验证的问题**。下面按严重程度 P0/P1/P2 分级列全。

## 一、P0（致命 / 会导致功能假死或误判）

### P0-1　小红书自动触达「必失败」——证据门禁与适配器契约自相矛盾
- **现象**：`XiaohongshuInteractionAdapter.send`（`interaction/builtin-adapters.ts:226-233`）只 `return { status, message }`，**不返回 `readbackText` 和 `evidenceUrl`**。
- **矛盾**：同文件 `capability.supportsReadback: true`（`builtin-adapters.ts:189`）声明支持回读，实际却不给回读数据。
- **后果**：`dispatchReply` 的证据门禁（`comment-acquisition.service.ts:497-502`）要求 `ok = status==='sent' && (readbackText 含回复 || evidenceUrl 非空)`。小红书永远缺这两项 → **所有小红书回复必判 `failed`**，并 `recordFailure` 喂熔断器。
- **结论**：小红书获客从「读评论」能跑通，但「回复」这一环**实际是死路**，且每次尝试都在给熔断器记失败。

### P0-2　`scanAccount` / `scanDm` 返回的 `replies` 字段是「死常量 0」
- **证据**：`comment-acquisition.service.ts:154` 和 `:346` 都是 `const replies = 0;`，函数体内**从未再赋值**。
- **后果**：前端拿到的 `replies`（已回复数）**永远是 0**，即便真的生成了回复文本。这是返回假数据，任何依赖该字段的统计/展示都会错。
- **性质**：典型的「字段定义了但没接线」，正是大王最反感的「假功能」。

### P0-3　`comment-acquisition` 的 `autoReply` 参数是「伪自动」——开了也不会自动发
- **证据**：`comment-acquisition.service.ts:227-242`（评论）、`:387-397`（私信）——`autoReply` 为 true 时**只打日志**「已生成回复，等待人工审核后发送」，`status` 恒为 `pending`，**从不调用 `dispatchReply`**。
- **后果**：UI 层「开启自动回复」的开关（`engagement/comment-acquisition/page.tsx:110-117` 有二次确认）是**空转**，用户以为开了自动获客，实际一条都不会发出去。真正的自动外发只发生在 growth 引擎和 ai-employee 两套里，`comment-acquisition` 完全没接。

## 二、P1（高风险 / 审计与数据边界分裂）

### P1-1　三套获客系统「审计/数据边界」分裂，同一「获客」三种存法
- **growth 引擎**：`GrowthAcquisitionConfig` / `GrowthLead` 走 Prisma（`growthAcquisitionRun` 表 + 本地 `growth-store.json`）。
- **ai-employee**：`AutoAcquisitionConfig` / 记录 / 去重键存**本地 JSON store**（`loadAutoAcquisitionStore`），不与 Prisma 统一 Lead 表同源。
- **comment-acquisition**：走统一 `leads` 表（`lead.repository.ts` upsert）。
- **后果**：用户在一个页面看到的「线索」和另一个页面的「线索」可能不是同一份数据；去重、审计、CRM 移交各做各的。`captureAutoAcquisitionLeads`（ai-employee）和 `captureGrowthLead`（growth）是两套 CRM 沉淀入口，字段口径不一致。

### P1-2　熔断器是「纯内存态」，进程重启即清零
- **证据**：`circuit-breaker.ts:12` 注释自己写明「进程重启即清零（符合"重启即重新试"）」，`entries` 是 `Map`（`:44`），无任何持久化。
- **后果**：30 分钟熔断期里如果服务重启（桌面端 daemon、3011 后端都有可能），熔断状态丢失 → 立刻继续发评论/私信，可能触发平台风控封号。对「自动获客」这种会真实触达外部平台的场景，内存熔断器风险偏高。
- **另外**：growth 引擎和 ai-employee 各自有节流/熔断逻辑，与这个 `CircuitBreaker` 是否打通未确认——至少 `comment-acquisition` 用的是这一套，另外两套未必复用。

### P1-3　去重键「昵称+文本前缀」兜底不可靠，且跨平台不隔离
- **证据**：`lead.repository.ts:69-71` —— 无 `externalUserId` 时用 `nick:${nickname}|${sourceText.slice(0,40)}` 做身份。
- **隐患**：
  1. 同一用户在不同平台（抖音/小红书）昵称相同、评论文本相似时，`dedupeKeyOf` 里虽然拼了 `platform`（`:75`），但**同一平台内**两个不同用户若昵称撞车且前 40 字评论相同，会被错误合并成同一条线索。
  2. 评论是动态的，前 40 字相同但后文不同（如「求链接」后面跟不同商品），会被误判为重复。
- **后果**：线索池里可能「丢人」或「错并」，直接影响获客质量与 CRM 客户档案准确性。

### P1-4　小红书/快手「能力声明」与「实际能力」不符，前端会误导
- **小红书**：`supportsReadback:true` 但 send 不给回读（见 P0-1）。
- **快手**：`KuaishouInteractionAdapter.read/send` 都 `throw`（`builtin-adapters.ts:246-258`），`supportsReadback:false` 倒是诚实，但 `supportedTasks:['comment-reply']` 声明「支持评论回复」，实际一调用就抛错。
- **后果**：前端平台能力注册表会显示快手「支持评论获客」，用户选了才发现执行时报「待接入」。这是「能力登记造假」。

## 三、P2（中低 / 健壮性与一致性）

### P2-1　`scoreLeadPotential` 是「关键词硬编码」，无模型、无行业自适应
- **证据**：`reply-engine.service.ts:190-241` —— 强/中意向、正面、负面全是写死的中文关键词数组。
- **隐患**：评分不区分行业（教培、电商、本地生活同一个词表）；「多少钱」对卖课的和对卖货的权重应不同，现在是拍脑袋的固定分（强+35/中+20/问句+15/负面-25）。
- **对比**：`lead-intelligence` 模块有 `lead-score.service`（更高级评分），但 `comment-acquisition` 用的是 `replyEngine.scoreLeadPotential` 这套简易版，两套评分体系并存，阈值（默认 45）口径也可能不一致。

### P2-2　`dispatchReply` 防篡改校验存在「空文本绕过」边界
- **证据**：`comment-acquisition.service.ts:445-451` —— `if (!replyText || (lead.latestReply && lead.latestReply.trim() !== replyText))`。
- **边界**：当 `lead.latestReply` 为 `null`（比如扫描时回复生成失败，`latestReply` 存了 null），此时 `input.replyText` 非空即可通过，**没有任何「已审核回复文本」可对比**。等于「审核通过的线索」可以带任意新回复文本发送。虽然后面 `assertReplyLead` 校验了 `sourceText` 一致（`:732`），但 `replyText` 在 `latestReply` 为空时不受约束。

### P2-3　`assertReplyLead` 校验了评论文本一致，但私信线索的 `commentText` 语义混乱
- **证据**：`comment-acquisition.controller.ts:80-86` 的 `replyLead` DTO 字段叫 `commentText`；私信线索也复用这个字段。`assertReplyLead` 里 `lead.sourceText.trim() !== input.commentText.trim()` 校验（`:732`）。
- **隐患**：私信场景字段名仍是 `commentText`，语义上是「消息文本」，命名与行为分离，后续维护易踩坑。已有一条 `sourceType` 修复历史（`:716` 注释），说明这个模块字段语义多次踩坑。

### P2-4　`captureAutoAcquisitionLeads` CRM 沉淀失败时「静默降级」，用户无感
- **证据**：`ai-employee.service.ts:1193-1203` —— CRM 捕获异常被 catch 后只 `logger.warn`，返回 `enabled:false, capturedCount:0`。
- **后果**：ai-employee 自动触达跑完了，但线索没进 CRM，用户侧只看得到「触达成功」，看不到「线索没沉淀」。对「获客→CRM 转化」这条商业闭环，静默失败是隐患。

### P2-5　`isGrowthTouchAlreadyCompleted` 幂等门用「文本指纹 + message 包含」判断，脆弱
- **证据**：`growth.service.ts:6583-6599` —— 靠 `haystack.includes(needle)` 且 `haystack.includes('触达'|'已完成')` 判断是否重复触达。
- **隐患**：把「是否已触达」绑定在 `message` 文案包含特定词上，一旦 message 文案改动，幂等门就失效；且 `needle` 是目标文本前 120 字，撞车概率随数据量上升。

### P2-6　growth 的「随机延迟」和「节流」只在 `scheduled/workflow` 触发时生效，手动执行不受节流
- **证据**：`growth.service.ts:1907-1910` 随机延迟仅 `trigger==='scheduled'|'workflow'`；同账号节流 `ACQUISITION_THROTTLE_MS`（`:1923` 附近）虽在 `executeConfig` 里检查，但需确认手动连续点「立即执行」是否真的被节流（代码里节流检查在随机延迟之前，理论上对 manual 也生效，但语义上「随机延迟」只有自动触发才有，行为不统一）。
- **隐患**：用户手动狂点「立即执行」能否被节流拦住，是风控兜底的关键，需真机验证。

### P2-7　前端孤儿组件 + 入口重定向，存在「死界面」
- **证据**：`apps/auto-acquisition/page.tsx:7-9` 只 `redirect('/growth/acquisition')`；`auto-acquisition-center.tsx` 是导出了 `AutoAcquisitionCenter` 但**全局无引用**的孤儿组件（前端 agent 已坐实）。
- **后果**：代码库存在「看起来是自动获客中心，实际没挂到任何路由」的死代码，维护者容易被误导。

### P2-8　`scanDm` 的 platform 推断逻辑有「undefined 兜底」隐患
- **证据**：`comment-acquisition.service.ts:294-305` —— platform 为 `undefined as unknown as 'douyin'` 时，靠 `accounts?.[0]?.type === 2 ? 'wechat-channel' : 'douyin'` 推断，如果 `accounts` 为空数组，`accounts?.[0]` 是 undefined，`=== 2` 为 false → 永远落 `douyin`。
- **隐患**：账号列表为空或查不到时，会静默按抖音走，可能读错平台私信。

## 五、根因归纳（三句话）

1. **「自动获客」是三套历史演进的产物**（comment-acquisition → ai-employee → growth），没有收敛成一套，导致「伪自动」「数据分裂」「能力声明不一致」同时存在。
2. **证据/回读门禁是「假闭环」**：小红书/快手根本没接通回读，却对外宣称支持，结果是把「真实触达」这一商业底线做成了「声明式成功」。
3. **风控与幂等都在「内存/文案」层面**，没有持久化和强唯一约束，跑在会真实触达外部平台的自动化场景里，风险被放大。

---

## 六、建议修复顺序（供大王决策，未动手）

- **P0 先清**：①小红书 send 补 `readbackText`/`evidenceUrl`（或把 `supportsReadback` 改 false + 前端如实显示「暂不支持自动触达」）；②删掉 `replies` 假字段或真正接线；③明确 `comment-acquisition` 的 `autoReply` 语义——要么真接外发门禁，要么前端去掉「自动」字样。
- **P1 次之**：统一三套系统的 Lead 落库口径；熔断器持久化（或至少落库）；去重键引入更强身份（平台 UID 优先已做，兜底需更稳）。
- **P2 最后**：评分体系统一、防篡改补 `latestReply` 为空的校验、CRM 沉淀失败上报告警。
