# 3010 项目「自动获客」逻辑核查报告

> 核查日期：2026-09-04
> 范围：后端获客管线、自动触发机制、前端配置与调度、护栏与缺口
> 结论先行：**3010 的「自动获客」实际由三套并行系统构成**，真正的「无人值守自动外发」主路径是 **growth 引擎的 scheduler daemon（多平台）**，叠加 **ai-employee 的 30s 轮询（仅抖音爆款视频）**；`comment-acquisition` 模块是**手动扫描 + 人工审核**模型，`autoReply` 是「伪自动」，从不真实外发。

---

## 一、总览：三套获客逻辑

| 系统 | 代码位置 | 触发方式 | 平台 | 是否真实自动外发 | 角色 |
|---|---|---|---|---|---|
| **A. growth 引擎 scheduler daemon** | `backend/src/modules/growth/growth.service.ts` | 后端 `@Interval(60_000)` 守护进程，按 `beginTime` 定时 | douyin / wechat-channel / wechat / wecom / xiaohongshu / kuaishong / gongzhonghao | ✅（armed 后真实触达） | **主获客引擎** |
| **B. ai-employee 自动调度器** | `backend/src/modules/ai-employee/ai-employee.service.ts` | 后端 `setInterval` 30s 轮询 | **仅抖音**（找爆款视频评论） | ✅（autoSend:true，无人值守） | 抖音爆款视频自动触达 |
| **C. comment-acquisition 模块** | `backend/src/modules/comment-acquisition/` | **纯手动**：前端点 `scan` / `scan-dm` | douyin / wechat-channel（私信）/ 小红书 | ❌（`autoReply` 只生成待审线索，外发需人工 `review→reply`） | 旧版评论/私信获客（手动） |

## 二、系统 A：growth 引擎 scheduler daemon（主自动路径，多平台）

### 2.1 自动触发机制（核心）
- `growth.service.ts:319` — `@Interval(60_000) async runGrowthSchedulerDaemon()`，每 60 秒触发。
- `growth.service.ts:321` — 进门先 `isGrowthSchedulerDaemonArmed()`，未武装直接 return。
- `growth.service.ts:327` — 对每个 target `acquireGrowthSchedulerLease`（按 `lockKey` 抢租约）+ `startGrowthSchedulerLeaseHeartbeat`（心跳），**多实例安全**，避免重复执行。
- `growth.service.ts:331` — `runScheduledConfigs(userId, { limit:3, trigger:'daemon' })`。
- 武装条件（来自 `getRuntimeStatus` 审计逻辑 `growth.service.ts:822-825` 与 `:7148-7160`）：需 `GROWTH_EXECUTION_ENABLED=true` + `GROWTH_SCHEDULER_DAEMON=true` + `GROWTH_SCHEDULER_REAL_DAEMON_ALLOWED=true`。缺 `REAL_DAEMON_ALLOWED` 时 daemon「已配置但未武装」，不算商用后台闭环。
- 定时粒度：per-config `scheduleEnabled=true` + `beginTime`（HH:MM，`growth.service.ts:1579` 默认 `09:30`），每天到 `beginTime` 进入执行队列（`getSchedulePlan` 计算 `ready` 状态）。

### 2.2 执行管线（`executeConfig` → `runScheduledConfigs`）
`executeConfig`（`growth.service.ts:1772`）逐层门禁，全部通过才触达：
1. **账号校验**：`accountHealth` 必须存在且 `loginStatus==='online'`，否则 `account_not_logged_in` / `captcha_required` 跳过（`:1828-1870`）。
2. **风控校验**：`riskStatus!=='normal'` → `account_risk_control` 跳过。
3. **日限额**：`remaining = dailyLimit - exposureCount <= 0` → `daily_limit_reached` 跳过。
4. **节流**：同账号 `ACQUISITION_THROTTLE_MS` 内重复执行 → `throttled`（防平台反爬）。
5. **人类化随机延迟**：仅 `trigger==='scheduled'|'workflow'` 时 sleep 2–8s（`:1908`）。
6. **能力门禁**：`growthAutoExecutionCapability` —— 小红书/快手自动触达未接入，`auto` 无人值守被拒；`confirm-first` 允许走「发现→候选沉淀线索池（partial，触达待人工）」（`:1921`）。
7. **外发**：`sendMode:'auto-send'` + `requireReadback:true`（`:6509` 等多处）。

### 2.3 自动触达的安全门禁（复核 #4）
- `riskMode==='auto'` 的任务，**必须**有 `autoApprovedAt` 审批留痕，否则 daemon 一律拒绝执行（`runScheduledConfigs:2559-2574` 的 `riskEligible` 门 + `executeConfig:1946-1957` 的硬拒绝）。
- 审批留痕在「启用任务 / 切到 auto」时由 controller 风险确认门写入（`createConfig:1590`、`updateConfig:1694-1720`）。
- 即：**`auto` 模式任务 = 启用时需操作员显式风险确认（留痕），之后由 daemon 无人值守自动外发**；`confirm-first`/`draft-only` 模式 daemon 只采集沉淀线索，不真实触达。

### 2.4 结果落库与 CRM 移交
- 候选 → 评分 → 选中 → 触达 → 线索写入统一 Lead 表（store/Prisma）。
- `crmService.captureGrowthLead`（`:2994`、`:5022`）把线索移交 CRM / 企微。
- `listRuns` / `fetchRunLive` 提供实时执行遥测（前端每 ~900ms–1.5s 拉增量事件，非 cron，是执行会话拉取）。

## 三、系统 B：ai-employee 自动调度器（仅抖音，30s 轮询）

- `ai-employee.service.ts:77` — `AUTO_ACQUISITION_SCHEDULER_MS = 30_000`。
- `ai-employee.service.ts:529-539` — `onModuleInit` 中 `isAutoAcquisitionSchedulerArmed()` 通过则 `setInterval(..., 30s)` 并 `unref()`；启动时 `recoverInterruptedAutoAcquisitionRuns()` 做崩溃恢复。
- **武装三重门** `isAutoAcquisitionSchedulerArmed()`（`:1164`）：
  `GROWTH_EXECUTION_ENABLED==='true'` **且** `AI_EMPLOYEE_AUTO_ACQUISITION_SCHEDULER==='true'` **且** `GROWTH_SCHEDULER_REAL_DAEMON_ALLOWED==='true'`。任一缺失，定时器不挂载。
- 管线 `runAutoAcquisitionPipeline`（`:1985` 起）：
  - `findDouyinHotVideoLeads`（`:2007`）—— 按关键词搜抖音爆款视频评论。
  - `planDouyinFollowUp` —— 评分阈值 `minScore:45`（`:2039`）。
  - `executeDouyinFollowUpCore({ autoSend:true })`（`:2107`）—— `sendMode:'auto-send'` + `requireReadback:true`。
  - 日限额 `config.dailyLimit`、去重 `autoAcquisitionDedupeKey`（`:2130`）。
  - 账号护栏 `getAutoAcquisitionAccountBlocker`（`:1114`）：抖音未登录即阻断。
  - 成功后 `captureAutoAcquisitionLeads` → `crmService.captureAutoAcquisitionLeads`（`:1045/1178`）。
- **特点**：发现层是「抖音爆款视频」而非「评论」，与 growth 引擎发现层不同；配置存本地 `AutoAcquisitionStore`（JSON/KV），不与 Prisma 统一 Lead 表共享同一审计边界。

## 四、系统 C：comment-acquisition 模块（手动，伪自动）

- 控制器 5 端点（`comment-acquisition.controller.ts:16-91`）：`scan`、`scan-dm`、`leads`(GET)、`leads/:id/review`、`leads/:id/reply`。
- `scanAccount`（`service.ts:74`）：归一化账号 → `assertAccountOwnership` 归属校验 → 经 `interactionRegistry` 读评论 → `replyEngine.scoreLeadPotential` 评分（`<minScore` 默认 45 跳过）→ `generateReply` → 互动事实入库 → `leadRepository.upsert` 单写统一 Lead 表去重。
- **`autoReply` 是伪自动**：`service.ts:231-242` 明确注释——「扫描阶段只允许生成待审核线索；真实外发必须由 approved Lead 经过 `dispatchReply` 后门禁触发」。`autoReply` 只生成 `pending` 线索，**绝不外发**。
- `scanDm`（`service.ts:268`）：读抖音/视频号私信（评论先校验归属，私信在外发前才校验归属，见 `:308`）。
- `dispatchReply`（`service.ts:423`）：**真实外发唯一门禁**。`assertReplyLead` 要求 `status==='approved'`（`:729`）+ 回复文本与库存一致（防篡改 `:446-451`）。经适配器 `send`，**强制回读/证据**——无 `readbackText` 或 `evidenceUrl` 即判 `failed`（`:497-502`）。
- `reviewLead`（`service.ts:597`）：approve→`approved`，skip→`skipped`。

### 回复引擎与风控（系统 C 共用）
- `reply-engine.service.ts`：7 种人格池（`personas.ts`，按权重轮换，`PersonaBinder` 同 key 绑同人格），`generateReply` 带禁词校验 + 换人格重试 ≤2 次；`scoreLeadPotential` 关键词打分（强意向+35/中+20/问句+15/负面-25）。
- `circuit-breaker.ts`：内存断路器，key=`platform:accountId`，10 分钟窗口失败 ≥3 触发，熔断 30 分钟。**进程重启即清零**。

## 五、统一获客管线（发现 → 触达 → 线索 → CRM）

```
发现层        comment-acquisition(评论/私信)  |  growth(关键词/账号/视频链接/目标账号)  |  ai-employee(抖音爆款视频)
   ↓
读取适配器    interaction/builtin-adapters.ts 统一契约 InteractionAdapterRegistry
              Douyin/WechatChannel: read→AutoUploadService.read*; send→PlatformInteractionExecutor.dispatch→local-engine
              Xiaohongshu: 独立 readComments/replyComment（send 不返回 evidenceUrl → 证据门禁必 failed）
              Kuaishou: read/send 均 throw（未接入）
   ↓
意向评分      replyEngine.scoreLeadPotential / comment-insights（PAIN/DEMAND/OBJECTION 规则）
   ↓
回复生成      replyEngine.generateReply（人格池 + 禁词校验 + 换人格重试）
   ↓
门禁           approved 状态门 / autoApprovedAt 审批留痕 / 账号登录态 / 风控 / 日限额 / 节流 / 能力门
   ↓
真实外发      dispatch (sendMode:'auto-send', requireReadback:true) 经 local-engine / agent-s / local-bridge（桌面 CDP/RPA）
   ↓
回读证据      必须 readbackText + evidenceUrl，否则 failed → 熔断器 recordFailure
   ↓
线索沉淀      统一 Lead 表（leads 模块 upsert / 去重 / 归因 lead-attribution / 转化 lead-convert）
   ↓
CRM/企微移交   crmService.captureGrowthLead / captureAutoAcquisitionLeads → 微信/企微承接
```

## 六、护栏 / 风控（全链路）

- **三重环境变量武装门**（两套 daemon 各自校验 `GROWTH_EXECUTION_ENABLED` / `GROWTH_SCHEDULER_REAL_DAEMON_ALLOWED` / `AI_EMPLOYEE_AUTO_ACQUISITION_SCHEDULER`）。
- **账号登录态 / 风控 / 验证码阻断**：未登录、风险态、需验证一律跳过。
- **日限额 + 同账号节流 + 人类化随机延迟**（防平台反爬）。
- **审批留痕门**：`auto` 模式必须有 `autoApprovedAt` 才允许无人值守外发。
- **状态门禁**：外发前 Lead 必须 `approved`，回复文本防篡改。
- **回读/证据强制**：无 `readbackText`/`evidenceUrl` 判 `failed`。
- **内存熔断器**：platform:accountId 失败 ≥3/10min → 熔断 30min。
- **崩溃恢复**：`recoverInterruptedAutoAcquisitionRuns()`（ai-employee）/ `migrateLocalStoreToDatabase()`（growth onModuleInit）。
- **租约 + 心跳**：growth daemon 多实例不重复执行。

## 七、关键缺口与风险（交底）

1. **两套自动系统发现层不同**：growth（关键词/账号/视频链接）+ ai-employee（抖音爆款视频）是独立调度，数据/审计边界未完全统一（前者 Prisma，后者本地 JSON store）。
2. **小红书 `send` 不返回 `evidenceUrl`/`readbackText`**：在证据门禁下必判 `failed`，自动触达实际不可用；**快手完全未接入**（read/send 均 throw）。
3. **熔断器为内存态**：进程重启清零，无跨重启持久化。
4. **`comment-acquisition` 的 `autoReply` 是伪自动**：容易被误读为「开了就自动发」，实际只沉淀待审线索。
5. **前端孤儿组件**：`apps/auto-acquisition/auto-acquisition-center.tsx` 无任何引用，入口已收敛到 `/growth/acquisition`；`apps/auto-acquisition/page.tsx` 仅 redirect。
6. **依赖本机 RPA 校准**：真实外发经 local-engine / agent-s / local-bridge（桌面 CDP），生产稳定性取决于本机浏览器 selector 校准，多处注释标记「selector 待接入」。
7. **安全底线**：AGENTS.md 硬规则——微信/桌面客户互动必须走 Agent-S，local-engine 不得替换其主执行器；默认 `auto-send` 但风险内容/不确定目标/权限不足时进入确认。
