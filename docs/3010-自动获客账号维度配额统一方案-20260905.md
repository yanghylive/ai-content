## 一、为什么现在才写方案（关键前提交底）

配额统一改造不是「加个计数器」那么简单。调研发现**三套账号体系 `accountId` 语义不一致**，是必须先定的硬门槛：

| 体系 | 用在哪 | accountId 语义 |
|---|---|---|
| `publishAccount`（Prisma） | comment-acquisition 校验（`assertAccountOwnership`） | stableId（`local-engine-…-6-douyin`）或纯数字 `6` |
| `accountHealth`（JSON store） | growth 触达定位 | `platform` + `accountId`（GrowthPlatform 串） |
| `PlatformAccount`（Prisma） | mobile-executor | 平台账号标识（如 xhs uid） |

**三者对不上。** 直接挂任一套都会「数错账号」、风控失效。

### 决策：锚定 `publishAccount.id`（stableId）

统一计数器 key = `userId + platform + publishAccount.id`。理由：

1. **它是唯一真实账号实体，且 comment-acquisition 已在用**（`assertAccountOwnership` 查的就是它）。
2. **growth 对齐成本可控**——`accountHealth.accountId` 本就源于账号，growth 扣减时按 `platform + accountId` 反查 `publishAccount` 拿 stableId 即可。
3. **`PlatformAccount` 不行**——`accountId` 是平台侧 uid，跟 comment-acquisition 的 stableId 对不上。

## 二、现状（坐实，非假设）

| 维度 | growth | comment-acquisition |
|---|---|---|
| 触达上限 | `dailyLimit`（默认 20，任务级） | **无**（只有熔断器） |
| 计数 | `exposureCount`/`exposureDate`（存 `GrowthAcquisitionConfig`，任务级） | 无计数 |
| 扣减 | `config.exposureCount + quotaConsumedCount`（growth.service.ts:4824） | 无 |
| 并发保护 | `liveRuns` Map 按 `userId+configId`（**任务级，非账号级**） | `circuitBreaker` 按 `platform:accountId` |

### 已坐实的并发漏洞

两个不同获客任务跑**同一个账号**时，各自 `liveRuns` 不互斥、各自 `exposureCount` 独立累加 → **同号并发触达，叠加突破平台安全阈值**。这正是统一配额要堵的洞。

## 三、方案设计

### 3.1 存储：独立计数表（不塞 config JSON）

**新增轻量表 `account_touch_quota`**（Prisma），不塞 `publishAccount.config` JSON，理由：

- JSON 字段无法原子递增（Prisma 对 Json 字段没有 `increment`，并发扣减会丢更新）。
- 独立表可用 `updateMany`/原生 SQL 做原子 `increment` + `where count < limit` 防超限。

```prisma
model AccountTouchQuota {
  id            String   @id @default(cuid())
  userId        String   @map("user_id")
  platform      String
  accountId     String   @map("account_id") // publishAccount.id（stableId）
  dailyLimit    Int      @default(20) @map("daily_limit")
  touchDate     String   @map("touch_date") // YYYY-MM-DD
  touchCount    Int      @default(0) @map("touch_count")
  createdAt     DateTime @default(now()) @map("created_at")
  updatedAt     DateTime @updatedAt @map("updated_at")

  @@unique([userId, platform, accountId, touchDate])
  @@index([userId, platform, accountId])
  @@map("account_touch_quotas")
}
```

### 3.2 扣减：原子、防超限、幂等

统一扣减服务 `AccountTouchQuotaService`，核心方法：

```
tryConsume(userId, platform, accountId): Promise<boolean>
```

- 用 `$transaction` 或原生 SQL：`UPDATE … SET touch_count = touch_count + 1 WHERE … AND touch_count < daily_limit`，`affectedRows === 1` 才算扣成功。
- **扣成功才允许真实触达**；扣失败返回 false，上层拦截（不发送）。
- 跨天自动切桶（`touchDate` 变化时新桶从 0 起）。

### 3.3 接入点（两处）

1. **comment-acquisition**：`dispatchReply` 成功分支前，`tryConsume` 成功才发、失败拦截（补上它现在完全缺失的触达上限）。
2. **growth**：真实触达扣减处（`executeConfig` 里 `quotaConsumedCount` 逻辑），从「任务级 `exposureCount`」改为「调 `tryConsume` 账号级计数」。

### 3.4 兼容与降级

- **任务级 `dailyLimit` 降级为「提醒」**：保留字段与前端展示，但不再作为硬拦截（硬拦截统一走账号级计数器）。
- **`perTargetLimit` 保留任务级**：单目标防骚扰策略，与账号级日总量正交，不合并。
- **迁移**：老数据不动，新计数器从 0 起（首次上线当天按 `dailyLimit` 默认 20 重新计）。

## 五、⚠️ 风险交底

1. **S-Q4 改现有 growth 风控语义**，是最大风险点——growth 现有 `dailyLimit` 拦截逻辑遍布 `executeConfig`（1918-1926）、`planItem.remainingToday`（2517/2562）多处，切换要逐处核对，避免「账号级拦了、任务级还在拦」双拦或漏拦。
2. **原子扣减的并发正确性**是核心，必须真测并发（不是 mock 单测能覆盖），否则又回到「同号穿透」。
3. **comment-acquisition 首次接入触达上限**，会让原本「无上限自动回复」的私信链路突然受 `dailyLimit` 约束——这是**预期行为**（风控必需），但要跟大王确认默认值是否合适。
4. 跨模块（growth + comment-acquisition 共用 service），要放在不产生循环依赖的模块（建议 `growth` 或独立 `account-touch-quota` 模块，由 growth 和 comment-acquisition 各自 import）。

### S-Q4 调研结论（坐实，非假设）

growth 的配额模型比 comment-acquisition 复杂得多：

1. **`exposureCount` 是任务级 config 字段**，同时充当「本次执行预算」（`remaining = dailyLimit - exposureCount`，传给 `fetchCandidatesWithAiEmployee`/`executePlatformFollowUp` 的 `maxTargets`）和「日累计计数」，遍布 20+ 处。
2. **真实触达链路**：`executeConfig`（1918-1926 算 remaining）→ `fetchCandidatesWithAiEmployee` → `executePlatformFollowUp` → `executeFollowUpViaDriver` 逐 target 调 `driver.execute`。配额在 `createRunResult`（4824）累加后持久化回 config JSON。
3. **关键难点**：growth 的 `config.accountId` 是前端原始字符串（`this.text(input.accountId)`），语义不统一（纯数字 id / stableId / accountHealth 串），与 comment-acquisition 已归一化的 stableId 对不上 → 切账号级前必须先归一化 accountId 到 `publishAccount.id`。

### S-Q4 两种切法（待大王拍板）

| 方案 | 做法 | 利弊 |
|---|---|---|
| **① 保守（推荐）** | 真实触达点 `executeFollowUpViaDriver` 逐 target 调 `tryConsume` 硬拦；任务级 `dailyLimit` 降级为「执行预算提醒」，不再硬拦（或保留但账号级优先） | 改动面小、不动现有风控语义、账号级是硬上限；但任务级 dailyLimit 仍可能先触发拦截（需一并放松） |
| **② 激进** | 彻底删任务级 `exposureCount`，全切账号级 `tryConsume` | 语义最纯，但动 20+ 处、config 持久化、remainingToday 展示、多处 planItem，风险高易翻车 |

**我的建议 = ①**：账号级 `tryConsume` 是真正的风控硬上限（同号跨任务穿透的洞在这堵），任务级 `dailyLimit` 保留为「单任务执行预算」不硬拦，避免大改 existing 语义。
