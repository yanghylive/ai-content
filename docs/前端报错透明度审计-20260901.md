# 前端报错透明度审计——"用户看到失败但不知道真实原因"全量盘点

> 生成：2026-09-01 00:43 · 起因：大王指令"举一反三，看看整个前端有多少报错是用户不清楚真实原因的"
> 方法：脚本解析 frontend/src 全部 886 个 catch 块（按括号配平提取、按反馈渠道归类）+ toast 文案全量枚举 + 结构化错误字段引用分布 + 逐文件核对兜底 UI 状态。静态扫描为主、关键点抽样人核。
> 结论先行：**基建是好的（public-error.ts 双工具 + API 客户端透传后端 message），但有 3 类系统性漏洞让真实原因到不了用户眼前**：①16 页加载失败纯 console（页面空白，分不清"没数据"还是"坏了"）；②操作失败真实原因只进 console、用户只见"请稍后重试"；③112 个文件只用 toPublicError，后端业务文案被设计性丢弃。

## 四、P1-系统性：后端给了原因，前端 toPublicError 设计性丢弃（112 文件）

机制：toPublicError 只认 5 类模式（401/403/429/超时/网络），命中才给对应人话；**后端业务文案如"该平台账号未授权，请重新绑定"不在 5 类内 → 一律替换成"操作未完成，请重试"**。toActionableError 就是为这类场景造的，但 112 个文件没用它。

重灾区（只用 toPublicError 的调用点数）：

| 模块 | 文件（处数） |
|---|---|
| 设置 | settings-integrations.tsx (12)、ai-service-settings.tsx (7) |
| 本地引擎 | local-engine 全家 15+ 文件（engine-files/engine-remote/engine-logs/engine-run-detail/ai-action/browser-agent 等） |
| 情报 Intelligence | monitors-center (6)、redfox-connection (6)、redfox-skills (4)、reports-workbench (4)、inbox-processing (3) 等 10+ 文件 |
| 能力中心 | model-form (3)、account-sections (3)、risk 三件 (5) |
| 平台 | platform-account-form (3)、platforms-center (1) |
| 策略/视频 | strategy-form (3)、product-cut (2)、release-plans (1) |
| 其他 | task-evidence-center (1)、today-center (1) 等 |

**改法（不能机械全换，要按点甄别）**：
1. 原则：**用户主动操作/表单提交类 catch → toActionableError**（后端业务校验文案本来就是写给用户看的）；页面加载类 catch → toPublicError（防技术细节外泄）。
2. 前提：后端 message 文案治理——确认对外接口的 message 不含堆栈/SQL/路径（toActionableError 已有 120 字 + TECHNICAL_DETAIL_PATTERN + 原始 JSON 三重过滤兜底，风险可控）。
3. 分批走：第一批 settings-integrations + platforms + materials + growth 相关（用户高频），第二批 intelligence/local-engine 全家。
4. ⚠️ 注意：toActionableError 的 120 字上限会把长文案截到不透出（回落 toPublicError），后端长报文需先在服务端摘要。
