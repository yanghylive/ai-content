# ai-content 前后端「单入口」改造方案

> 版本：v1.0 ｜ 日期：2026-08-09 ｜ 状态：待评审
> 关联版本：1.1.70（桌面）｜ 影响范围：本地 3010 / 桌面内置静态服务 / 前端 API 基址逻辑

---

## 1. 背景：为什么要改

近两天桌面端/本地链路连续出现同一类问题，全部根源于**三端入口不一致**：

| 现象 | 表面原因 | 深层根源 |
|---|---|---|
| 微信登录点完「没有找到这个页面」 | 前端用了相对路径 `/api/auth/wechat/start`，打到纯静态服务 → 404 | 桌面/本地入口**没有 /api 反代** |
| 「redirect_uri 参数错误」 | 3011 被残留进程占用，读不到配置跳了 test 域名 | 进程管理问题（与端口无关，但暴露了链路脆弱） |
| getApiBase 里一坨 loopback 判断 | 前端要自己判断「该直连 3011 还是走同源」 | 前端被迫在**绝对地址/相对路径**间二选一，两端混用 |

**核心矛盾**：生产（nginx）一直正常，因为它是标准的「单入口 + /api 反代」；桌面内置静态服务和本地 3010 偷懒没做反代，前端被迫用绝对地址直连 3011，一旦端口/进程/配置有任何偏差就翻车。

**结论：不是两个端口的错，是入口不统一 + 前端地址策略混乱。这次改造把它们一次对齐。**

---

## 2. 目标架构：一套后端，三端各入口，全部同源

```
┌────────────┐   /api/* 反代   ┌──────────────┐
│ 浏览器/桌面 │ ──────────────▶ │  后端 3011   │
│  (前端静态)  │   同源相对路径   │  (NestJS)    │
└────────────┘                └──────────────┘
        ▲ 每个端都有自己的「入口」，入口负责两件事：
        │   ① 服务前端静态文件  ② /api/* 转发给后端
```

| 端 | 入口 | /api 反代 | 现状 |
|---|---|---|---|
| 生产 web（vip） | nginx | ✅ 有 | 正常，**不动** |
| 移动 App 壳 | 壳内网关 | ✅ 有 | 正常，**不动** |
| 本地开发 3010 | 现为裸 `npx serve` | ❌ 无 | **本次补** |
| 桌面内置静态服务 | `main.js` 的 `createFrontendStaticServer` | ❌ 无 | **本次补** |

改造后前端**一律用相对路径 `/api/...`**，无跨域、无绝对地址 hack、无需任何 loopback 判断。

## 3. 现状差距分析（代码级）

| 位置 | 现状 | 差距 |
|---|---|---|
| `desktop/main.js:462` `createFrontendStaticServer` | 纯静态，非 `/api` 路径一律 404 | 缺 `req.url.startsWith('/api')` 转发分支 |
| 本地 3010 启动方式 | `npx serve out/`（裸） | 需换成带反代的静态服务脚本 |
| `frontend/src/lib/api/client.ts` `getApiBase()` | 30+ 行 loopback/域名判断，返回绝对地址 | 简化为一句话：同源 `/api` |
| `frontend/src/app/login/page.tsx` 微信按钮 | 已改 `getApiBase()` 拼绝对地址（hack） | 反代就绪后可回退为相对路径 |
| 反代实现参考 | 工作区 `serve-static.mjs`（http.request 转发到 3011 + `.html` fallback）已具备完整逻辑 | 复用/搬入项目 |

## 4. 改造内容（分模块）

### 4.1 本地开发 3010 —— 换成带反代的静态服务
- 把现成 `serve-static.mjs`（`/api` 转发 3011 + `.html` fallback + SPA 路由回退）搬入项目 `scripts/`，作为本地标准起服务方式
- 启动命令从 `npx serve out/` 改为 `node scripts/serve-static.mjs`（`API_TARGET=http://127.0.0.1:3011` 可配）
- 收益：本地与生产行为完全一致，微信按钮、登录、AI 能力全部同源

### 4.2 桌面内置静态服务 —— `main.js` 加 `/api` 反代
- `createFrontendStaticServer` 增加分支：`req.url` 以 `/api/` 开头 → 用 `node:http` 转发到 `127.0.0.1:3011`（后端端口），流式回传（照抄 serve-static.mjs 的 `proxyApi` 逻辑）
- 转发需透传：method / headers（含 Cookie、Content-Type）/ body 流
- 超时与错误处理：后端未启动时返回 502 + 明确文案（「后端服务未启动，请稍候」），避免白屏
- **端口仍用 3010 做前端、3011 做后端**，但浏览器视角只有一个 origin

### 4.3 前端 —— `getApiBase()` 简化为同源
- `getApiBase()` 改为直接返回 `/api`（同源相对路径），删除 loopback 判断全段
- 保留一个例外：显式配置 `NEXT_PUBLIC_API_BASE` 指向**非 loopback 域名**（如云端部署）时仍走绝对地址（后端不在同一域名下的场景）
- 微信登录按钮、AI 能力等所有调用点回归相对路径（原 hack 一并回退）

### 4.4 打包与守卫
- 桌面打包后需验证：`resources/frontend/` 内 chunk 里 API 调用为相对路径、无 `localhost:3011` 字面量残留
- `release-guards.js` / `check-full-installer-assets.js` 增加「包内无绝对 3011 地址」检查项

## 6. 验证方案

### 6.1 本地 3010（改造后）
1. `node scripts/serve-static.mjs` 起服务
2. 浏览器打开 3010，检查 Network：所有请求 origin 都是 3010，无 3011 跨域请求
3. 微信登录全链路（扫码 → 回跳）✅
4. 账号密码登录、AI 对话/生图/语音各验一次
5. 后端故意停掉 → 刷新应看到「后端未启动」502 提示而非白屏

### 6.2 桌面打包（1.1.70）
1. 解包 `app.asar` / 检查 `resources/frontend/`：grep `localhost:3011` 应为 0
2. 真实启动 Electron：登录、微信登录、AI 能力全链路
3. 断网/后端异常场景：明确报错不白屏

### 6.3 回归
- 验收门禁 `commercial-acceptance-gate.mjs` 全绿（基线 PASS=50）
- 生产 web（nginx）回归：不受影响，抽验登录页

## 7. 风险与回滚

| 风险 | 等级 | 对策 |
|---|---|---|
| 桌面反代引入回归（如 Cookie 透传漏） | 中 | 严格透传 headers；验收门禁覆盖登录态链路 |
| 本地 3010 行为变化影响日常开发 | 低 | 起服务方式更新到 README/启动脚本，一步到位 |
| 打包守卫误伤 | 低 | 守卫只加「无绝对 3011」，不碰域名白名单 |

**回滚**：桌面回退 = 重打上一版包；本地 3010 = 换回 `npx serve`。改动集中在入口层，无数据/库表风险。

## 9. 改造后的长期收益

1. **同类问题绝迹**：相对路径/绝对地址混用、loopback 判断、微信按钮 404 这类问题从根上消失
2. **三端行为一致**：本地、桌面、生产、移动壳同一种入口模式，问题排查口径统一
3. **前端更简单**：删掉 30+ 行环境判断代码，新人也能看懂
4. **为后续多端扩展铺路**：新端（如 WebView 壳）照抄同一入口模式即可
