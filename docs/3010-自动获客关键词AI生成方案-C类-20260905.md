## 一、结论先行

**现状：代码里没有「AI 分析行为生成关键词」的能力，这是一条要新建的闭环，不是改参数。**

现有三处关键词/评分全是**纯规则查表**，零 LLM 参与：

| 位置 | 现状 | 代码证据 |
|---|---|---|

**但底子已齐**：行为数据（`LeadSignal` 表 + `Lead.matchedKeywords/signals`）、LLM 能力（`AiClientService`）、写回目标（`GrowthStrategyTemplate` 三个 string[]）全都有，**缺的只是把它们串起来的「语义归纳」这一环**。

## 二、C 类要解决的业务问题

B 类跑通后，获客策略的关键词是「人工拍脑袋 + 行业词库」出来的，两个痛点：

1. **词库泛、不准**：行业词库（如美业「多少钱/价格」）是通用词，但你的真实客户可能全在问「穿戴甲」「睫毛胶水」这种长尾痛点词——通用词搜出来的评论 90% 是噪音，真客户藏在长尾词里。
2. **零反馈闭环**：哪些词带来过真客户、哪些词是纯噪音、哪些词触发了对方拉黑/举报，**从没回流去修正下一轮搜索词**。等于每次搜索都从零开始。

C 类解决的就是：**让系统从真实线索行为里「学」出下一轮该搜什么词。**

## 四、C 类闭环设计（核心）

```
┌─────────────────────────────────────────────────────────────┐
│  行为数据采集（已存在，C 类只补 negative 信号）                │
│  LeadSignal: engagement.reply / engagement.repeat /          │
│              intent.* / risk.spam / negative(补)             │
│  Lead: matchedKeywords / sourceText / customerId / status    │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  KeywordIntelligenceService（新建，C 类核心）                 │
│  输入：某账号/行业近 N 天线索聚合 + 正负反馈                   │
│  调用：AiClientService → LLM 语义归纳                         │
│  输出：结构化关键词建议 + 每条建议的证据归因                    │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  写回（需人工确认，非自动覆盖）                                │
│  sourceKeywords / demandKeywords / excludeKeywords           │
│  → 更新 GrowthStrategyTemplate（走 updateStrategy）           │
│  → 前端展示「AI 建议词 + 采纳/忽略」按钮                       │
└─────────────────────────────────────────────────────────────┘
```

### 4.1 输入：给 LLM 喂什么

不是把原始评论一股脑丢给 LLM，而是**先聚合、后归纳**：

```json
{
  "industry": "美业",
  "window": "最近 30 天",
  "positive": [
    { "text": "穿戴甲能做吗多少钱", "signal": "intent.price", "converted": true },
    { "text": "有睫毛嫁接吗", "signal": "intent.question", "converted": false }
  ],
  "negative": [
    { "text": "又是广告取关了", "signal": "negative" },
    { "text": "别刷了烦不烦", "signal": "negative" }
  ],
  "current": {
    "sourceKeywords": ["美甲", "皮肤管理"],
    "demandKeywords": ["多少钱", "价格"],
    "excludeKeywords": ["招聘", "招商"]
  }
}
```

关键设计：**每条样本带 `converted`（是否成交）+ `signal`（正/负反馈）标注**，让 LLM 做的是「有监督归纳」而非「无脑提取」。

### 4.2 LLM 的输出（严格 JSON Schema）

```json
{
  "sourceKeywords": ["穿戴甲", "美甲款式", "美甲工作室"],
  "demandKeywords": ["穿戴甲", "睫毛嫁接", "多少钱", "能上门吗"],
  "excludeKeywords": ["招聘", "招商", "带货", "教程"],
  "rationale": [
    { "keyword": "穿戴甲", "reason": "近 30 天 12 条成交线索都提到「穿戴甲」，现有词库无此词", "evidenceCount": 12 }
  ]
}
```

约束：**LLM 只做语义归纳，不碰执行**。输出的关键词仍要过 `excludeKeywords` 白名单过滤 + 人工可改（对齐「系统填 80%、用户只改不填」）。

### 4.3 安全红线（对齐底座红线 + 拒绝假功能）

1. **AI 建议不自动覆盖策略**：产出走「建议 → 前端展示 → 人工采纳/忽略」，不直接写库。避免 LLM 幻觉词污染线上策略。
2. **LLM 不补造证据**：`rationale` 每条必须带 `evidenceCount` 归因，无证据不出词（对齐 `lead-score.service.ts:315`「不得补造来源」的既有原则）。
3. **计费走 kaypal 统一网关**：复用 `AiClientService`，不新开计费通道。

## 六、风险与依赖（交底）

| 项 | 风险 | 说明 |
|---|---|---|
| 模型网关 | 中 | 依赖 kaypal 模型网关 + 账号有模型额度。无额度时 C 类不可用，需降级为「规则版自动补词」（见 §七） |
| Prompt 质量 | 中 | LLM 归纳长尾痛点词的质量取决于 prompt + 样本量。样本 <10 条时归纳不可靠，需设「最少样本阈值」 |
| 幻觉词 | 中 | LLM 可能产出行业无关词，必须过 excludeKeywords + 人工确认双闸 |
| 计费成本 | 低 | 走 kaypal 统一计费，每次归纳是一次 LLM 调用，成本可控 |
| 隐私 | 低 | 线索文本喂 LLM 需确认用户授权边界（对齐底座治理红线） |

## 七、降级方案（大王关注的「稳妥」）

如果模型网关不可用 / 样本不足，C 类先做**规则版自动补词**（不接 LLM）：

- 从 `Lead.sourceText` 用「高频词统计」提取热词（分词 + 停用词过滤 + 频次排序），反哺 `sourceKeywords`/`demandKeywords`。
- 轻量、零依赖、无幻觉风险，先让「反馈回流」跑起来。
- LLM 版（语义归纳 + 同义聚类）作为后续增强，与规则版共用同一套「建议 → 人工确认 → 写回」链路。

**建议 C 类内部再分两级**：C-a（规则版自动补词，先跑通反馈闭环）+ C-b（LLM 语义归纳，增强）。C-a 无真机/网关依赖，可先落地；C-b 等网关稳定后再上。
