## 一、评估结论速览

| 项 | 结论 | 建议 |
|----|------|------|
| **D2 微信群发/朋友圈** | **不建议本阶段立项** | 合规风险高（封号/平台协议）、依赖未落地的桌面微信原生运行时、回报不确定 → **降级为「能力边界文档 + 前端占位引导」** |
| **D3 抖音深度互动** | **建议分两步立项** | 第一步（P1）：**链接曝光/作品详情回读**（可复用 RedFox + RPA，低风险）；第二步（P2）：**搜索/定向**（依赖平台风控，需真实账号灰度） |

**一句话**：D3 的「链接曝光/回读」是现有能力（RedFox 采集 + 设备 RPA）的自然延伸，可低成本落地；D2 的「群发/朋友圈」当前工程底座（桌面微信原生运行时）尚未实现真实驱动，且腾讯对群发/朋友圈自动化的风控明确，**先不做**。

## 二、D2 微信群发/朋友圈评估

### 2.1 现状（代码实证）

- **能力声明**：`local-engine.wechat-command.mixin.ts` 定义了 `wechat-moments-publish`（朋友圈发布）、`wechat-moments-marketing`（朋友圈营销）等任务类型；`wechat-native.mixin.ts` 有 `moments-publish`/`moments-marketing` 命令分支。
- **真实执行链路**：`tryRunWindowsWechatNativeControlledTask`（wechat-native.mixin.ts:624）**只在 `win32` 平台返回非 null**——即需要**桌面 Windows 微信原生运行时（runWechatNativeRuntimeCommand）**，该运行时是否已实现真实驱动**未确认**（本机为 macOS，无法验证）。
- **macOS 侧**：`contact.mixin` 已有降级提示（D1 已闭环：非 darwin 平台给出「仅支持 macOS 与 Windows」提示），但**macOS 上微信自动化本身依赖窗口读取/DB 解密**，属于桌面端既有能力，手机端无入口。
- **RPA 可行性**：手机端 RPA（无障碍）理论上可驱动微信 App 做群发/朋友圈，但——微信是**风控最严的平台**：自动化群发/朋友圈发布触发异常检测（频繁操作/新设备/群发特征）→ 封号风险极高；且微信 App 内无障碍节点对「发送朋友圈」「群发」入口的语义支持有限。

### 2.2 合规边界分析

| 维度 | 分析 | 结论 |
|------|------|------|
| **平台协议** | 微信用户协议明确禁止自动化群发/营销行为；朋友圈自动化发布属于「外挂/脚本」范畴 | 🔴 高风险 |
| **封号后果** | 触发风控轻则功能限制（群发/加人受限），重则封号——用户账号资产不可逆损失 | 🔴 高风险 |
| **法律责任** | 批量群发可能触达《反不正当竞争法》/用户骚扰投诉；营销内容合规（广告法）难自动化保证 | 🟡 中风险 |
| **产品信任** | 承诺「微信群发」后用户账号被封，将直接损害产品信任与口碑 | 🔴 高风险 |

### 2.3 结论与建议

**不建议本阶段立项**。理由：① 工程底座（win32 微信原生运行时真实驱动）未落地且属桌面端范围；② 合规/封号风险高，收益（微信群发营销）不确定；③ 即便实现，手机端 RPA 驱动微信自动化的风控风险更高。

**已执行动作（2026-08-09 定案：功能下线）**：
1. **能力边界文档**明确「微信群发/朋友圈：不支持，原因：平台风控与合规」——避免用户误以为可自动化群发。✅
2. **前端入口全部移除**：侧边栏「微信群发」「朋友圈」导航已删；微信任务中心「群发消息」「发布朋友圈」「朋友圈营销」卡片已删；高级工作台「欢迎语群发」按钮已删；`WECHAT_MODULES`/`WECHAT_PLAN_FILTERS`/`WECHAT_PLAN_TYPES` 已剔除群发/朋友圈类型。✅
3. **7 个相关路由改为「暂不支持」提示页**（含原因说明：平台风控可能导致封号）：`/engagement/wechat-groups`、`/engagement/wechat-moments`、`/wechat-moments-v2`、`/workbench/wechat-moments`、`/workbench/wechat-v2/mass-send`、`/workbench/wechat-v2/moments-publish`、`/workbench/wechat-v2/moments-marketing`——直达 URL 也不会再看到可用功能。✅
4. 消息页微信入口文案由「会话、群发、朋友圈、加好友」改为「会话、加好友」。✅
5. ~~保留 `wechat-moments-*` 任务类型的人工半自动~~（已放弃：半自动入口本身也是误导，用户拍板前端不留任何入口）。

## 三、D3 抖音深度互动评估

### 3.1 现状（代码实证）

- **已有能力**：
  - **RedFox 采集**（已配置上线）：作品信息、去水印素材采集——`/api/redfox/collect/link` 链路已通（真实链接可用）。
  - **CDP 会话**：`cdp-browser-profile.service.ts` 已有 douyin session 管理（桌面浏览器自动化）。
  - **设备 RPA**（已上线）：手机无障碍驱动抖音 App 调起/操作，任务链路（创建→领取→执行→回传）已闭环。
  - **互动审批闸门**：risk-policy 已有 `interaction-approval`、`publish` 等高危动作审批模型，可复用。
- **缺口**：抖音**搜索/定向/曝光**类深度动作（搜索指定关键词→定向互动→提升曝光）**没有现成动作实现**——既有 CDP 链路是桌面发布侧，RPA 是通用调起/输入，未针对「抖音搜索→定向评论/关注」编排。

### 3.2 分步方案

#### P1（建议先做）：链接曝光/作品详情回读
- **内容**：输入抖音作品链接 → 回读作品详情（标题/作者/数据）→ 生成互动建议（评论文案/关注建议）→ 人工确认后一键调起抖音处理。
- **技术**：复用 RedFox 采集（回读详情）+ 回复建议生成（reply-v2 已有）+ 手机「一键转发/调起」（mobile-bridge 已有）——**全是现有能力的组合，零新底座**。
- **风险**：低（只读回读 + 人工确认发送）。
- **工作量**：约 1-2 人天（前端编排页 + 后端接口组合）。

#### P2（后置）：搜索/定向互动
- **内容**：抖音内搜索关键词 → 定位目标作品/账号 → 自动评论/关注/私信（定向）。
- **技术**：设备 RPA 扩展（无障碍驱动抖音搜索框输入→结果点击→目标操作）；或桌面 CDP 抖音搜索链路。
- **风险**：高（抖音对自动评论/关注风控明确：新号/频繁操作触发异常检测，定向批量互动有封号风险）。
- **前置**：需真实账号灰度验证风控阈值；建议**每次操作人工确认**（复用 interaction-approval 审批闸门），并加频控（如每账号每日 ≤ N 次）。
- **工作量**：约 3-5 人天（RPA 动作编排 + 审批集成 + 频控）。

### 3.3 结论与建议

**建议立项 P1**（链接曝光/回读——低风险、纯现有能力组合、可直接落地）；**P2 立项需真实账号验证风控阈值后决策**（当前模拟器无法验证，先不承诺）。

## 四、决策建议汇总

| 项 | 建议 | 动作 | 估时 |
|----|------|------|------|
| D2 微信群发/朋友圈 | ❌ 本阶段不做 | 能力边界文档 + 前端占位引导（半自动复制方案备用） | 0.5 人天 |
| D3 P1 链接曝光/回读 | ✅ 立项做 | 后端接口组合 + 前端互动页（复用 reply-v2 模式） | 1-2 人天 |
| D3 P2 搜索/定向 | 🟡 暂缓，等真实账号灰度 | 立项文档 + 频控/审批设计（不写实现） | 0.5 人天 |

**我的推荐**：**D3 P1 直接开工（无阻塞、可立即验证），D2 与 D3 P2 落地为「边界文档 + 占位引导」**。这样 D 批以「一个可用的新能力（链接曝光回读）+ 两个合规结论」收口，不给用户留下「承诺未兑现」的坑。
