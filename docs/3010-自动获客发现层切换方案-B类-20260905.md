# 3010 自动获客 B 类专项方案 —— 快手/小红书「统一切关键词搜索模式」

> 状态：待大王 review，未动代码。
> 前置：A 类 7 条已收尾（6 commit + 1 tech debt），本方案是最后一块大项。
> 目标：让快手/小红书从「未接入/通知中心假成功」切换到 growth 已验证的「关键词搜索 → 内容详情页 → 读评论 → 回复」真实现链路，彻底闭合自动获客。

---

## 一、问题本质（为什么必须做发现层改造，不是 adapter 层能解决的）

坐实的事实链：

| 平台 | 现状 | 卡点 |
|---|---|---|
| **快手** | `KuaishouInteractionAdapter` 纯 `throw`（`interaction/builtin-adapters.ts:243-262`），`supportsReadback:false` 但 `supportedTasks:['comment-reply']` 假声明 | 没接 RPA driver |
| **小红书** | `XiaohongshuInteractionAdapter.send` 走老 `XiaohongshuInteractionExecutor`，从「通知中心」读评论，`item.ref` 是通知条目 index，**拿不到内容详情页 URL** | 通知中心模式天然无 contentUrl |
| **真实现** | `DiscoveryBrowserRunner.readComments({contentUrl, keyword})` / `replyComment({contentUrl, keyword, targetText, replyText})` 已实现，回复带 `evidenceUrl` 截图、填框校验、防误发阻断（`discovery-browser-runner.ts:363-596`） | **需要 contentUrl + keyword** |

**核心矛盾**：`DiscoveryBrowserRunner` 的 read/reply 都需要 `contentUrl`（内容详情页 URL），但 `comment-acquisition` 的 `scanAccount` 发现层走 `interactionRegistry.read({platform, accountId, limit})`（`comment-acquisition.service.ts:118-123`），**根本没有 contentUrl 来源**。

而 growth 引擎早就跑通了「关键词搜账号 → 读作品拿 workUrl → 读评论(contentUrl=workUrl) → 回复」这条链路（`growth.service.ts:5780-5905`），天然有 contentUrl。

**结论**：要「不降级」地接真实现，必须给 `comment-acquisition` 新增「关键词搜索」发现入口，复用 growth 的 contentUrl 链路。这是发现层改造，不是改一个 adapter。

---

## 二、改造总览（三层，自底向上）

```
[发现层]  scanAccount 新增「关键词搜索」模式：keyword → 搜账号 → 读作品 → 拿 contentUrl
[适配层]  KuaishouInteractionAdapter / XiaohongshuInteractionAdapter 注入 DiscoveryBrowserRunner
          read/send 从「通知中心/throw」切换为「runner.readComments / runner.replyComment」
[契约层]  InteractionReadInput / InteractionSendInput 补 contentUrl + keyword 字段
          scanAccount/scanDm 入参补 keyword，透传给 adapter
```

## 六、风险与交底

1. **真机依赖是硬门槛**：S-B2/S-B3/S-B4 每步接 runner 后，必须真机跑通才算完成。快手/小红书选择器若 growth 之后平台改版，可能需要重新校准 `COMMENT_SELECTORS`。
2. **小红书「通知中心」是旧数据源**：切到「关键词搜索」后，旧「通知中心」模式被替代。若用户依赖「通知中心」的某个特性（如「我收到的评论」），需确认无回归。
3. **配额（已定：账号维度统一配额，共用）**：`DiscoveryBrowserRunner` 有 `AcquisitionQuotaService` 配额（`assertQuota`）。已定方案——把 `dailyLimit`（每日触达上限）上提到**账号维度**的统一触达计数器，growth 与 comment-acquisition 切 runner 后**共用一个「账号日触达配额」**，同号累计扣减、扣完即停；`perTargetLimit`（单目标别重复骚扰）保留任务级策略不合并。理由：风控本质是「这个账号今天对外发了多少条」，与发起方无关；若两边独立计数，同号会叠加触达、突破平台安全阈值。
4. **S-B3 删老 executor**：`XiaohongshuInteractionExecutor` 可能还被别处引用（需 grep 确认），删除前要坐实无其他调用方。

## 八、已拍板的 2 个决策点（2026-09-05）

1. **关键词来源（已定：B 类先跑通，AI 生成独立成 C 类）**：
   - B 类（本方案）的关键词**来源定为两路并用**：① 用户扫描时**手动输入**（S-B4 前端加输入框，快手/小红书时显示）；② 复用 growth 的「获客策略」`sourceKeywords`/`demandKeywords` 词库（`growth-keywords.data.ts` 的 14 行业词库）作为默认词。这样 B 类不依赖 LLM，链路先闭合。
   - 「AI 分析行为逻辑、自动生成关键词」这条能力**独立成 C 类专项**，不塞进 B 类。C 类闭环：已有线索行为信号（`LeadSignalStore` + `matchedKeywords` + 成交/回复正负反馈）→ 喂 LLM 语义归纳 → 产出下一轮 `sourceKeywords`/`demandKeywords`/`excludeKeywords` → 写回 strategy 供下一轮搜索。AI 只做语义归纳、不做执行，生成词仍过 `excludeKeywords` 白名单 + 人工可改（对齐「系统填 80%、用户只改不填」）。
   - 现状交底：现有 `generateStrategy` 是纯模板查表（`growth.service.ts:1364` → `defaultIndustryTemplate`，从 14 行业写死词库取值），`LeadScoreService` 是纯规则匹配（`lead-score.service.ts:65` 注释明写「不接 LLM，纯规则」），**目前没有任何 AI 生成关键词的能力**，需新建。

2. **配额（已定：账号维度统一配额，共用）**：`comment-acquisition` 切到 runner 后，快手/小红书发现受 `AcquisitionQuotaService` 配额约束。**与 growth 共用同一套「账号日触达配额」**（`dailyLimit` 上提到账号维度统一计数器），不独立。详见第六节第 3 条。
