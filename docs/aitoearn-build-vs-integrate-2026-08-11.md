# AiToEarn 二选一评估：它接进我们 vs 我们接进它（2026-08-11）

> 结论先行：**选 A——AiToEarn 接进我们系统**（作为外部 API 服务/通道），不选 B（我们重写进它）。
> 决定性因素：我们是**桌面端 + 本地自动化**产品，B 路线在架构上承载不了我们独有的功能。

## 一、两条路线的定义

- **A 路线（它接进我们）**：ai-content 保持主系统（桌面端/获客/CRM/AI 助手/本地账号）。
  AiToEarn 作为外部服务：① 模型中转 = AI 供应商（接 DeepSeek 一样的姿势）② 发布 = 后端加一个 provider 调它 Flow API（补海外平台）③ 它的状态机/平台抽象作为参考（MIT 可抄）。
- **B 路线（我们接进它）**：AiToEarn 为主系统，把我们独有的功能（桌面端自动化、获客、CRM）改造成它的子模块/插件。

## 二、六维对比（基于两边源码事实）

| 维度 | A 路线（它接我们） | B 路线（我们接它） |
|---|---|---|
| **产品形态** | ✅ 我们桌面端（Electron+本地引擎）原样保留 | ❌ 它是 **Web 服务**（Next.js+Mongo 无桌面端），我们的微信自动化/本地浏览器获客在 web 架构里**跑不起来**，要重写 |
| **账号模式** | ✅ 我们本地 cookie（账号在自己机器）不变，海外可走它 relay | ❌ 全面切它模式 = 账号授权托管官方（放弃本地账号控制） |
| **数据/技术栈** | ✅ 我们 Prisma/Postgres+SQLite 不动，只加 API 依赖 | ❌ 它 MongoDB+Redis+RustFS，我们数据层要整体迁移/适配 |
| **扩展机制** | ✅ 它开放 API（X-Api-Key）是标准外部服务接口 | ❌ 它**没有插件/扩展体系**（源码无 plugin 机制），我们要改它核心代码 |
| **改造量** | 小：加 AI 供应商记录 + 一个发布 provider | 大：桌面产品 web 化 + 数据迁移 + 账号模式重构 |
| **成熟度利用** | ✅ 同样能享受它发布/模型/状态机成熟度（通过 API + 抄设计） | ✅ 全盘继承，但代价是丢差异化 |

## 三、B 路线的三个硬伤（为什么否掉）

1. **形态不兼容**：我们是桌面客户端（本地 CDP 自动化、微信 4.x 数据库、本地文件素材），它是纯 Web 服务——我们的核心能力在它架构里没有载体，等于重写产品且丢掉桌面价值。
2. **账号模式倒退**：B = 放弃"账号 cookie 在自己手里"，全走 relay/托管第三方，合规与安全不可控。
3. **无插件机制**：它没设计"第三方业务子系统"扩展点，硬塞 = fork 维护，升级即冲突。

## 四、A 路线落地三步（按 ROI）

1. **模型中转**（今天已备好方案，零代码）：ai-platforms 加 `baseUrl=https://aitoearn.cn/api/ai` + key → Gemini/Claude/DeepSeek/GPT 全通；Seedance/GPT-image-2 走开放平台异步任务。
2. **海外发布通道**：后端新增 `aitoearn-publish.provider`（调它 Flow API：账号授权→创建 Flow→轮询记录），补 TikTok/YouTube/IG 等 8 个海外平台；国内平台保持本地自动化。
3. **发布状态机升级**（参考它的 flows/records/scheduler/tasks 设计）：我们发布记录补 重试/取消/改时间/作品链接回读。

## 五、风险清单（A 路线）

- 海外发布依赖它 API 稳定性 + credits 计费（第三方单点）
- 海外账号授权走它（relay）→ 账号托管官方，需合规评估（国内账号不走它，不受影响）
- 缓解：API 层隔离（provider 可切换），它挂了不影响我们国内链路
