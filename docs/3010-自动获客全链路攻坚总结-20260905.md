## 六、账号维度配额统一（堵「同号多任务穿透」漏洞）

方案文档：`3010-自动获客账号维度配额统一方案-20260905.md`

**背景**：三个配额数各算各的，还有个漏网之鱼——
1. growth：任务级 dailyLimit（按任务算，开 3 个任务同号发 60 条）
2. comment-acquisition：压根没配额，只有熔断器
3. 并发漏洞：liveRuns 锁按任务锁，同号并发会互相踩计数器

**方案**：配额挂到「账号」头上，一个账号今天对外触达总量统一 20，growth 和评论/私信获客共用同一个计数器，扣完即停。

**三个关键决策（大王拍板）**：
1. 账号 ID 锚点 = `publishAccount.id`（stableId，唯一认准一个号）
2. 默认日触达上限 = 20（私信链路也先 20，跑起来再调）
3. 存储 = 独立表 `account_touch_quota`（原子扣减必需，不塞 config JSON）
4. 配置入口 = 先不做 UI，默认 20 跑，真机验证后再考虑

| commit | 步骤 |
|---|---|
| `7af97976` | S-Q1 AccountTouchQuota 表 + 手写 migration（绕开 dev 库漂移 reset） |
| `047e16ab` | S-Q2 AccountTouchQuotaService（原子 tryConsume + resolveStableId + getTodayUsage） |
| `d1db18d4` | S-Q3 comment-acquisition dispatchReply 接入 tryConsume |
| `247f57cd` | S-Q4 growth 触达切账号级（保守：预算合并 + 成功入账 + 降级不阻断） |

**核心机制**：
- `tryConsume`：`UPDATE ... SET touch_count = touch_count + 1 WHERE touch_count < daily_limit`，affectedRows===1 才算扣成功（原子防并发超发）。
- `tryConsumeN`：批量扣，`touch_count + n <= daily_limit` 才整体 +n（growth 触达完成后一次性入账成功数）。
- `resolveStableId`：把数字 id / stableId / 平台串统一归一化成 publishAccount.id。
- growth 切法选「保守」：任务级 dailyLimit 保留当执行预算，账号级做硬上限，解析失败降级不阻断主流程。

验证：growth.service.spec 106 全绿 + account-touch-quota 11 全绿 + comment-acquisition 15 全绿；tsc 零错误。

⚠️ **并发正确性需真机/真并发验证**（mock 单测覆盖不了同号穿透）。

## 七、遗留回归根治（commercial spec 3 条失败）

**根因**：`c74d4c0a`（9/3 他人提交）把 preflight 从「真实探活」改成「只看持久化快照」（`force:false`），且兜底逻辑只生成写死的 default 账号、不生成任务绑定账号快照 → 首次 preflight 匹配不到账号 → 误判「未找到可验证的执行账号」。

**根治（commit `362f3803`）**：
1. preflight 回退真实探活（`force:true`）——preflight 语义是「执行前最后一道检查」，必须反映账号真实状态；真实探活实测 ~2.6s，非作者担心的 12s（那是单账号 headless 探活耗时，preflight 不触发）。
2. `ensureAccountHealth` 兜底补 task rows——为任务绑定但未探活到的账号生成 needs-human 快照，防账号凭空消失。

验证：growth 3 套 127 测试全绿；tsc 零错误。
