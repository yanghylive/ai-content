依赖瘦身决策清单

合并方案完成后，5 个底层依赖（Node/Python/PostgreSQL/Redis/Chrome，~554 MB）能不能砍？怎么砍？本清单帮你做决策。

📅 D1 = 2026-06-03 📦 当前 5 个依赖 / 554 MB 🎯 目标 1-2 个 / 145-502 MB ⏱️ 决策需时：半天 🔧 实施需时：1-3 天

📊 现状：5 个依赖，554 MB

依赖体积装它干啥装了之后的体验
Node 20 25 MB 跑 3011 后端 NestJS 命令行可用，但日常用不到
Python 3.11 25 MB 跑 5409 auto-upload（CDP 浏览器自动化） 用户看不到；Python 包占空间
PostgreSQL 16 357 MB 存用户账号、任务、配置数据 起本地 DB 服务；用户感知"有个服务在跑"
Redis 3.0 1.7 MB 缓存、消息队列 起本地 Redis 服务
Chrome 145 MB CDP 自动化控制抖音/视频号网页 用户能看到 Chrome 图标（首次装后）

首装体验（用户视角）

装完 89 MB 主程序后，首次启动还要下载 472 MB 的依赖。下载 + 装要 5-15 分钟（看网速）。

用户会看到一个进度条，然后是 macOS 4 项权限引导对话框。这套体验你已经做过（v1.1.0），但"装得多"是用户抱怨的常见来源。

🎯 三个目标方案对比

A. 极致瘦身

只剩 Chrome

Node 跟 Electron 走 / Python 干掉（Local Runtime 改 Node 写）/ PostgreSQL 干（数据上云）/ Redis 干

依赖：1 个 / 145 MB

最轻 最简单 用户友好

B. 平衡

Chrome + PostgreSQL

Node 跟 Electron 走 / Python 干 / Redis 干；PG 留下（数据本地）

依赖：2 个 / 502 MB

数据安全 可离线用 中等复杂度

C. 保守

全保留 + Node 干掉

砍 Node（Electron 带），其他全留（5409 仍 Python，PG/Redis 不动）

依赖：4 个 / 529 MB

改动最小 体积大 5409 仍活着

推荐方案 A（下面有详细理由）。如果你接受，砍 Python + 干 PG/Redis + 改 Local Runtime 全 Node 化；如果担心数据隐私或云成本，方案 B 是稳妥选择。

🔍 逐个依赖：留还是砍？

1. Node 20（25 MB）

✅ 必砍

理由：Electron 主程序内置 Node 运行时（`electron` 二进制本身就是个 Node + Chromium 复合体）。用户装 Electron app 后，命令行有 Node 但不能单独"用 Node"，要靠 Electron 进程。

怎么砍：不需要显式"砍"。部署时不要再单独提示用户装 Node；安装脚本里把 Node 那一项从 deps 移除就行。

风险：极低。Electron 一直内置 Node 10+。我们用 Node 20 的特性，Electron 28+ 内部都用 Node 20。

2. Python 3.11（25 MB）

✅ 推荐砍（方案 A/B 都砍）

当前用途：5409 auto-upload 服务（CDP 自动化）

合并后能不能 Node 化？：能。P2 我新建的 LocalRuntimeEngineClient 是 HTTP 客户端，浏览器自动化可以让 Node 端的 Puppeteer/Playwright 做（不调 Python）。

砍 Python 要做的事：

  1. 把 P2 阶段的 Local Runtime 真正 Node 化（不再调 127.0.0.1:5409 那个 Python 服务）
  2. 用 Playwright 替代 5409 的 CDP 控制逻辑
  3. 写 Node 版 BrowserControlService（CDP 控制、preflight、状态机）
  4. 本地安装脚本里删除 Python 检测/下载步骤

风险：中。5409 跑过 3 轮 build 稳定，改成 Node 等于重写一部分浏览器自动化逻辑。要做完整测试。

省下：25 MB（Python 包）+ 简化部署 + 减少一个"用户不知道为什么存在"的语言运行时

3. Chrome（145 MB）

✅ 必留（三个方案都留）

为什么：抖音/视频号网页版对 Chrome 特征检测很严，必须用真实用户级 Chrome（不能是 Electron 内嵌 Chromium），否则登录、扫码、风控都过不去。

但可以考虑的优化：

  • 方案 A-1：让用户自己装 Chrome（如果系统已有就不重复装；省下载时间）
  • 方案 A-2：用 Playwright 自带 Chromium（包大 200MB+ 但免用户装，抖音不一定能用）
  • 方案 A-3（推荐）：保持现状装 Chrome，但检测系统已有 Chrome 不重复装

风险：低。Chrome 是 v1.1.0 已经搞定的。

4. PostgreSQL 16（357 MB）

⚠️ 看数据架构决策

当前用途：存用户账号、任务记录、配置、AgentSession 等

两个选择：

维度保留（方案 B）干掉（方案 A）
数据存哪用户本地 PG云端数据库（如 Supabase / Neon / RDS）
成本用户机器性能 / 占空间云端按量付费
离线用✅ 可以❌ 断网不能用
数据隐私✅ 在用户机器⚠️ 在云端（需合规）
用户感知本地有个"服务在跑"无感知

建议：

  • 如果客户是 ToB 商业客户（企业用户，介意云合规）→ 保留本地 PG（方案 B）
  • 如果客户是 个人创作者（散户，能接受云端）→ 干 PG 上云（方案 A）

5. Redis 3.0（1.7 MB）

✅ 推荐砍（三个方案都砍）

当前用途：缓存 + 消息队列

为什么能砍：

  • P2 我做的 EvidenceService 是 fire-and-forget，不需要 Redis 队列
  • 缓存可以用 进程内 Map 替代（数据量小、用户单机使用）
  • 单进程 Node 没必要起个 Redis 服务

风险：低。需要审计现有代码：是不是有其他地方真用 Redis（任务队列？分布式锁？）。如果没有，直接砍。

🌲 决策树（按顺序问）

问题 1: 数据存哪？ ├── 本地（用户机器）→ 必须留 PG → 选方案 B └── 云端 → 砍 PG → 进入问题 2 问题 2: 客户能接受云端数据吗？ ├── 介意（ToB / 企业）→ 选方案 B（保留本地） └── 不介意（个人 / 散户）→ 选方案 A（干 PG） 问题 3: 客户能接受首装下载 145 MB（Chrome）吗？ ├── 不能接受 → 选方案 A-2（Playwright 自带 Chromium，~200MB+） └── 能接受 → 选方案 A-1（保持现状装 Chrome，145 MB） 问题 4: 你愿意重写 Local Runtime 浏览器自动化吗？ ├── 不愿意 → 选方案 C（保守，保留 5409 Python） └── 愿意（1-2 天） → 选方案 A（彻底 Node 化） 最终推荐路径： ToC 个人创作者 + 愿意重写 → 方案 A（极致瘦身 145 MB） ToB 企业客户 + 数据本地 → 方案 B（平衡 502 MB） 想最小改动 → 方案 C（保守 529 MB）

🛠️ 实施方案 A 的迁移步骤（推荐）

前置条件

  • P3 真机完成（双跑 0 差异、5409 归档）
  • P4 桌面端集成完成（Electron 拉起 Runtime）
  • 数据上云决策已定（云服务商、schema 迁移方案）

步骤 1：Local Runtime Node 化（2-3 天）

  1. 把 P2 的 LocalRuntimeEngineClient 升级为 Local Runtime 真服务端（不是只调 5409 的客户端）
  2. 用 Playwright 替代 5409 的 CDP 控制逻辑
    • 新增 runtime/local-engine/playwright-runtime.service.ts
    • BrowserControlService 加 Node 版实现（不调 Python）
  3. 端到端测试：抖音/视频号评论/私信 4 互动 × 5 轮
  4. 移除 LocalRuntimeEngineClient 里的 127.0.0.1:5409 硬编码

步骤 2：数据上云（1-2 天）

  1. 选云服务商（建议：Supabase 起步快 / Neon serverless PG / RDS 稳）
  2. Prisma schema 改 datasource provider：postgresql → 留 postgresql（连接云端 URL）
  3. 迁移脚本：本地 PG 数据 → 云端 PG（一次性）
  4. Prisma migrations 改成连云端（DATABASE_URL 改）
  5. 本地不再起 PG 服务

步骤 3：缓存改进程内（半天）

  1. 审计现有 Redis 用法（grep -rn "ioredis\|redis\." backend/src/）
  2. 如果有 → 改成 Node Map 或 lru-cache 包
  3. 如果没有 → 直接删依赖
  4. 部署脚本移除 Redis 检测/下载

步骤 4：装器瘦身（半天）

  1. 修改 desktop/installer.nsh：删除 Node/Python/Redis 步骤
  2. 修改 desktop/installer/deps-manifest.json：只剩 Chrome
  3. 修改 desktop/installer/detect-deps.ps1：检测逻辑更新
  4. CI: .github/workflows/release-desktop.yml deps 上传步骤只剩 Chrome

步骤 5：测试 + 发布（1 天）

  1. 在测试机装新构建版本，验证 472 MB → 145 MB
  2. 跑完整 8 节验收 9 项
  3. v1.2.0 发布

⚠️ 风险与缓解

风险概率影响缓解
Playwright 替代 5409 行为不一致 中 高 双跑期 3 天验证差异 = 0（同 P3-D2/D3）
数据上云迁移丢数据 低 致命 本地保留 PG 一段时间；双写云+本地；用户确认后切换
云服务成本失控 低 中 Supabase/Neon free tier 起步；监控使用量
客户不能接受云数据 中 高 保留方案 B 兜底；按客户群分流
Node 化 Local Runtime 引入 P0 bug 中 高 P2 阶段保留旧路径；新路径加 feature flag

⏱️ 时间估计

方案依赖实施时间最终体积用户首装体验
A 极致瘦身 Chrome (145 MB) 4-6 天 145 MB 下完即用（~2-3 分钟）
B 平衡 Chrome + PG (502 MB) 1-2 天 502 MB 中等等待（~5-8 分钟）
C 保守 Chrome + PG + Python + Redis (529 MB) 0.5 天 529 MB 等待（~6-10 分钟）

时间对比：方案 A 投入最多（4-6 天），但收益最大（用户首装体验最爽）。方案 B 投入最少（1-2 天），适合"快速改进"心态。方案 C 几乎不投入，但保留所有现状。

🎯 我的推荐

如果你的客户群是个人创作者（ToC）：选方案 A

理由：

  • 用户首装体验差距巨大（145 MB vs 472 MB）
  • 个人用户对云数据不敏感（接受 SaaS 模式）
  • 砍 Python = 简化部署 / 减少 1 个"用户不知道为什么存在"的语言运行时
  • 砍 Redis = 单进程 Node 足够，不再起服务

成本：

  • 云数据库 ~$25/月（100 用户规模）
  • Supabase free tier 起步够用（500 MB 数据库 / 50k MAU）

如果你的客户群是企业（ToB）：选方案 B

理由：

  • 企业用户对数据本地化要求高
  • 断网可用对企业是关键
  • PG 留下但 Redis 仍可砍（不重要）
  • 砍 Python 仍可做（用 Playwright 替代）

最终：方案 B = Chrome + PostgreSQL = 502 MB
