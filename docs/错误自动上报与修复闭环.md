# 错误自动上报与修复闭环（v1.1.89+）

> 从 v1.1.89 起，JIUZHANG AI 桌面端具备**错误自动上报**能力：任何运行异常会自动采集并上传云端，无需用户手动收集日志。配合每日自动检查，形成「上报 → 检查 → 分类 → 自动修复（留人工发版闸）」的闭环。

## 一、背景

2026-08 真机反馈：Windows 用户在「创建获客任务」「CRM 操作」时报错，但报错文案是通用兜底文案（`创建获客任务失败，请稍后重试`），真实根因被吞掉。要定位必须拿到用户机器的后端日志，流程是：写收集脚本 → 传 OSS → 用户下载双击 → 压缩发回 → 人工看堆栈。**链路太长、太被动**。

因此把日志收集内建进安装包：**报错自动上传服务器，AI 定时检查、自动修复、按需发版**。

## 二、上报链路（已上线）

```
用户机器异常
 ├─ 后端 500（AllExceptionsFilter 捕获）
 │    └─ reportError() → OSS error-reports/<date>/<uuid>.json
 └─ 前端异常
      ├─ window.onerror / unhandledrejection（ErrorReportBridge）
      └─ API 5xx（ApiError 带 requestId）
           └─ POST /api/error-report/client（后端代理）→ OSS 同上
```

### 报告内容（schema: error-report/v1）

| 字段 | 说明 |
|---|---|
| `app` / `version` | ai-content-desktop / 应用版本（主进程注入 APP_VERSION） |
| `requestId` | 精确关联后端日志（AllExceptionsFilter 打印同 id） |
| `method` / `url` | 出错的请求路由 |
| `status` / `message` | HTTP 状态 + 错误信息 |
| `stack` | 错误堆栈（≤8000 字符） |
| `system` | 平台/版本/架构/CPU/内存/主机名 |
| `occurredAt` | 出错时间（ISO 8601） |

### 关键代码位置

- 后端采集：`backend/src/common/filters/error-report.ts` + `http-exception.filter.ts`
- 前端代理端点：`backend/src/modules/error-report/error-report.controller.ts`（POST `/api/error-report/client`，`@Public`）
- 前端全局捕获：`frontend/src/lib/error-report-bridge.tsx`（挂 `providers.tsx`）
- 前端 API 5xx 上报：`frontend/src/lib/api/client.ts` 的 `request()`

### 配置

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `ERROR_REPORT_ENABLED` | `true`（未设置即开） | `false` 关闭上报 |
| `APP_VERSION` | 主进程注入 `app.getVersion()` | 上报版本号来源 |
| `OSS_ACCESS_KEY_ID/SECRET/BUCKET/REGION` | 打包注入（backend.env） | 上报落盘目标 |

**安全设计**：
- 限流：同一 requestId 只报一次；30 秒窗口最多 5 条（防错误风暴打爆 OSS）。
- 上报失败静默（`catch` 吞掉），绝不影响主流程。
- 报告不含用户 token / 密码 / 敏感数据，只含堆栈与系统信息。
- OSS 凭据进安装包的风险说明：该 key 本就随安装包用于自动更新下载（半公开资源），追加 `error-reports/` 写权限影响有限。

## 三、检查与修复闭环（模式 B：自动修复 + 手动发版）

**每日 9:30 自动任务**（WorkBuddy automation）执行：

```
1. 扫 OSS error-reports/（今天+昨天，排除 test-*/e2e-* 测试报告）
2. 每条报告分类：
   ① 可自动修复的代码 bug（堆栈指向项目代码、根因清晰）
   ② 环境/数据问题（用户机器数据、外部服务、需真机复现）
   ③ 无法定位（堆栈不完整）
3. 处理：
   ① → 直接改代码 → tsc 验证 → git commit（fix(error-report): 前缀）
        → **不打包、不上传、不发版**
   ② → 不改代码，报告根因与下一步
   ③ → 标记待人工
4. 输出中文报告：
   每条：时间/版本/路由/status/message/requestId/分类
   已修复：文件+改动要点+验证结果+commit，注明「新版本已准备好，等待确认后发版」
```

### 铁律

- **绝不自动发版**：修复完只出报告，等明确说「发版」才执行完整发版流程（见 `ai-content-desktop-release` skill）。
- **高风险改动不自动做**：数据库迁移、schema 变更、权限模型改动等，即使能修也停下报告等人工确认。
- 发版必须走全量门禁：`scripts/pre-release-full.mjs`（L1 单测 / L2 构建 / L3 真实功能 / L4 包内容，15 项全过才可发）。

## 四、排查指南（收到报告后怎么用）

1. **拿 requestId**：报告里的 `requestId` 与后端日志 `[AllExceptionsFilter] [<requestId>] <method> <url> <status>` 一一对应。
2. **看 version**：先确认用户跑的是哪个版本（`unknown` 表示主进程未注入，属异常，按升级处理）。
3. **看 stack 归属**：
   - `backend/src` / `frontend/src` → 代码 bug，可走自动修复。
   - `node_modules` 内部 / 原生模块 / 网络层 → 环境或依赖问题。
4. **常用复核**：
   ```bash
   # 列出今日报告
   node -e "..." # 用 ali-oss 列 error-reports/<date>/
   # 本机复现（云电脑真机环境，见 wuying-clouddesktop-test skill）
   ```

## 五、手动触发检查

在 WorkBuddy 里说「检查一下错误上报」即可手动跑一轮（等价于每日任务，不依赖定时）。

## 六、已知边界

- **Windows 真机微信链路**（桌面微信截图、OCR 兜底）需真机授权，上报不了也修不了，BLOCKED 属预期。
- **真实发布/自动执行**类错误需要真实账号对象，自动修复不覆盖。
- **外部依赖故障**（kaypal 网关、平台登录）不属于代码 bug，自动修复会停下报告。
