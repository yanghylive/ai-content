# 3010「自动获客」修复方案

> 版本：v1（待大王确认后实施）
> 日期：2026-09-05
> 前置结论：不涉及 AGENTS.md 红线（微信/桌面互动仍走 Agent-S，默认 auto-send 不动，本方案只修获客链路的正确性/诚实性/边界问题）。

---

## 0. 修复总原则（对齐大王硬约束）

1. **先诚实，后增强**：凡「声明了能力但实际没接通」的，第一步是**如实降级**（去掉假声明、前端如实提示），而不是硬补一个不稳的实现。
2. **每修一条独立 commit + 升版本号**（跨项目铁律：修复后必升版本号，否则自动更新链死）。
3. **改动前先核实、E2E 必抓 bug**：P0/P1 修完必须走「静态检查 + 单测 + 真实启动冒烟」，不能只过门禁。
4. **不碰底座红线**：用户/订阅/积分/治理不动；本方案只动获客链路本身。
5. **微信/桌面互动主执行路径 Agent-S 不变**：本方案不改 Agent-S 路由，只修 `comment-acquisition` / `growth` / `ai-employee` 的获客正确性。

## 2. S1 阶段：P0 止血（3 个）

### S1-1　修复小红书/快手「必失败 + 能力声明造假」（P0-1 + P1-4 合并）

**问题链**：`XiaohongshuInteractionAdapter.send` 不返回回读/证据 → `dispatchReply` 证据门禁下小红书必 failed；快手 read/send 全 throw 却声明 `supportedTasks:['comment-reply']`。

**方案（分两步，先诚实后增强）**：

- **步骤 A（必做，诚实降级）**：
  - `interaction/builtin-adapters.ts:189` 把小红书 `supportsReadback` 改为 `false`（与现状一致）。
  - 快手 `capability`（`:241-243`）把 `supportedTasks` 改为 `[]`、`adapterVersion` 降 `0.0.1`，明确「未接入」。
  - 前端平台能力注册表读到 `supportsReadback:false` / `supportedTasks:[]` 时，**评论获客页对小红书/快手显示「暂不支持自动触达，仅支持扫描沉淀线索」**，去掉「回复」按钮或置灰。
- **步骤 B（增强，可选，P1 优先级）**：
  - 小红书 `XiaohongshuInteractionExecutor.replyComment`（`xiaohongshu-interaction.executor.ts:72-158`）补回读：发送后回读 DOM 是否出现回复文本（`page.evaluate` 查输入框下是否有刚发的内容），返回 `readbackText`；截图存 OSS 返回 `evidenceUrl`（复用现有证据链）。
  - 若短期内无法稳定回读，则**维持步骤 A 的降级**，不硬上。

**验收**：
- 小红书 `dispatchReply` 不再「静默判 failed」，而是**在能力门就返回明确 reason**（`not_integrated` 或 `review_required`），不喂熔断器失败。
- 快手选平台时前端直接提示「待接入」，不走到 `throw`。
- 单测覆盖：小红书 send 返回体字段断言、快手能力声明断言。

**文件**：`interaction/builtin-adapters.ts`、`xiaohongshu-interaction.executor.ts`、前端评论获客页 + 能力注册表。

---

### S1-2　修复 `replies` 死常量 0（P0-2）

**问题**：`comment-acquisition.service.ts:154` 和 `:346` 的 `const replies = 0` 从未赋值。

**方案**：二选一，推荐前者——
- **方案 1（推荐）**：`replies` 字段语义改为「本次扫描实际生成了回复文本的条数」，在循环里对 `replyText` 非空时累加。这样前端「已生成回复」数真实。
- **方案 2（若该字段确无消费方）**：从返回体 `Promise<{...}>` 类型和前端 API client 里**彻底删掉 `replies` 字段**，避免假数据残留。

**验收**：扫描返回的 `replies` 与「生成了 replyText 的条数」一致；单测覆盖 `scanAccount` 返回体 `replies` 断言。

**文件**：`comment-acquisition.service.ts`、`comment-acquisition.controller.ts`（DTO 若含）、`frontend/src/lib/api/comment-acquisition.ts`。

---

### S1-3　明确 `autoReply` 语义：要么真接外发，要么去「自动」字样（P0-3）

**问题**：`comment-acquisition` 的 `autoReply` 开了只打日志，`status` 恒 `pending`，从不外发。

**方案（推荐去「自动」化，符合「默认 auto-send 但风险确认」原则）**：
- **前端**：`engagement/comment-acquisition/page.tsx` 把「开启自动回复」开关**改名为「生成回复草稿」或直接移除**，明确这是「扫描 + 生成候选回复 + 人工审核」的**手动获客**工具，不再暗示「自动」。
- **后端**：`autoReply` 参数**标记 deprecated**（保留兼容，避免前端老版本报错），但注释与返回体明确「扫描阶段只沉淀待审核线索」。
- **若大王确实要「评论获客也自动发」**：那必须走 `dispatchReply` 的 `approved` 门禁 + 审批留痕（对齐 growth 的 `autoApprovedAt`），这是另一套改造，另起任务，不塞进本次止血。

**验收**：前端无「自动回复」误导文案；后端 `autoReply=true` 时返回体 `status` 仍为 `pending` 且带明确 message「已生成回复草稿，待人工审核」。

**文件**：`engagement/comment-acquisition/page.tsx`、`comment-acquisition.service.ts`（注释 + 返回体 message）。

## 3. S2 阶段：P1 固本（4 个）

### S2-1　收敛三套系统的线索落库与 CRM 沉淀口径（P1-1）

**问题**：growth=Prisma、ai-employee=本地 JSON store、comment-acquisition=统一 leads 表；CRM 沉淀两个入口。

**方案（渐进，不一次重构）**：
1. 先**盘点并文档化**三套的 Lead 字段口径差异（产出对照表），确认哪些字段能统一。
2. **短期**：`ai-employee` 的 `AutoAcquisitionConfig/Record` 至少把「成功线索」同步写进统一 `leads` 表（复用 `LeadRepository.upsert` 的 `fromGrowthLead` 映射），不再只留本地 JSON。
3. **中期**：CRM 沉淀统一走 `crmService.captureGrowthLead` 一个入口，`captureAutoAcquisitionLeads` 内部转调它或明确标记为 legacy。

**验收**：同一用户在不同页面看到的是同一份线索；CRM 客户档案不因入口不同而重复建档。

**文件**：`ai-employee.service.ts`（capture 落库）、`growth-lead-bridge.service.ts`、`lead.repository.ts`。

---

### S2-2　熔断器持久化（P1-2）

**问题**：`circuit-breaker.ts:44` 内存 Map，重启清零。

**方案（轻量，不引入 Redis）**：
- 给 `CircuitBreaker` 增加**可选持久化后端**（`PrismaService` 写 `circuit_breaker_state` 表，或复用现有 KV）。
- `recordFailure` 触发熔断时写库；`getStatus` 时先查库再查内存（库优先）。
- 桌面端单进程场景可继续用内存，但 3011 后端多实例/重启场景用持久化。

**验收**：模拟熔断后重启服务，熔断态仍在（不立刻继续发）；单测覆盖持久化读写。

**文件**：`circuit-breaker.ts`（构造注入可选持久化）、新增 migration（若用表）。

---

### S2-3　去重键加固（P1-3）

**问题**：`lead.repository.ts:69-71` 昵称+文本前 40 字兜底，昵称撞车/前 40 字相同会错并。

**方案**：
- `dedupeKeyOf` 在「无 externalUserId」分支，把兜底身份从「昵称+前 40 字」升级为「昵称+完整文本 sha256 前 16 位 + 平台 + 账号」，降低撞车。
- 更彻底：对可拿到 `externalUserId` 的平台（抖音/视频号已有 authorId）优先用 UID，这个已经做了；补的是「拿不到 UID 时」的兜底要更稳。
- 增加**人工合并预览**（`mergeLeads`/`dedupePreview` 已存在，见前端 growth.ts），让用户对可疑合并做人工确认。

**验收**：构造两个「同昵称、前 40 字相同、后文不同」的评论，不再被合并；单测覆盖。

**文件**：`lead.repository.ts`。

---

### S2-4　能力声明诚实化（P1-4，与 S1-1 联动）

已并入 S1-1。此处补：**growth 引擎的 `growthAutoExecutionCapability` 已对小红书 `ready:false`、快手放行**，需与 `comment-acquisition` 的能力门对齐——避免「growth 说不行、comment-acquisition 硬发」。

**方案**：`dispatchReply` 在发之前加一层 `interactionRegistry` 能力预检（`capability.supportsReadback` / `supportedTasks` 含该 taskType），不满足直接返回 `not_integrated`，不进证据门禁。

**文件**：`comment-acquisition.service.ts`（dispatchReply 前置能力检查）。

## 5. 版本号与发版策略（跨项目铁律）

- **S1/S2 每个修复独立 commit + patch 升一版**（如 v1.1.101 → v1.1.102 → …），改完即走「假旧版升级 E2E」验证自动更新链不断。
- **版本号三处同步**：`package.json` + 前端 release-notes 页 / layout 常量 / login 页脚 / release-notes.md。
- **发布前门禁**：静态检查 + 单测 + 安全门禁（`pre-release-full.mjs` 四层）全绿才打包。
- **关键改动先在 jz-win11-\* 云电脑跑完整 E2E** 再宣告完成，尤其 P0-1/P1-4 涉及小红书/快手平台选择器。

## 6. 验收清单（整体）

1. 小红书/快手在获客页**如实显示能力**，不再「选了才发现死路」。
2. 扫描返回的 `replies` 真实、`autoReply` 不再误导。
3. 三套系统线索落库口径收敛（至少 ai-employee 写进统一 leads 表）。
4. 熔断态跨重启保留。
5. 去重不再错并。
6. `dispatchReply` 对未接入平台**能力门拦截**，不进证据门禁、不误记熔断失败。
7. 所有改动带单测 + 真机冒烟证据，commit 内交底 mistake/lesson。
