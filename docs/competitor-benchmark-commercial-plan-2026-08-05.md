# JIUZHANG AI 商业化对标与稳定性推进方案

日期：2026-08-05  
版本：V1.0  
适用范围：JIUZHANG AI 内容创作、发布、客户互动、桌面端与移动端

## 1. 目标与结论口径

本方案用于回答三个问题：

1. JIUZHANG AI 与参考产品“炼刀 AI 员工”的能力差距在哪里。
2. 哪些差距是商业化必须补齐的，哪些只是产品取舍。
3. 在不复制对方代码、资源、私有协议或凭据的前提下，如何把可验证的用户结果和稳定性补到商用门槛。

本次先完成方案、对比和证据登记，再进入实现。未达到“可验证”级别的能力不标记为已商用；仅有页面、按钮、路由或文案不算能力完成。

## 2. 两套独立对比方法

### 方法 A：用户任务链路法

以用户最终结果为中心，从入口一直跟踪到外部平台结果和系统回读。每条链路必须记录：

| 环节 | 必须回答的问题 |
|---|---|
| 前置条件 | 账号、权限、额度、平台登录、租户状态是否明确 |
| 用户动作 | 用户实际点击、填写、确认了什么 |
| 执行动作 | 系统调用了哪个执行器、在哪台设备、使用哪个账号 |
| 外部结果 | 平台是否真的发布、发送、评论、点赞、加好友或完成其他动作 |
| 回读证据 | 系统能否读取平台结果并关联任务 ID、账号和租户 |
| 失败处理 | 超时、登录失效、额度冻结、平台拒绝时是否可重试、取消或人工接管 |
| 用户感知 | 成功、失败、处理中和需要登录是否清楚且不混淆 |

这套方法比较“能不能完成用户任务”，适合发现假完成、状态不一致、页面有能力但后端不能执行的问题。

### 方法 B：运行时可靠性法

不从页面出发，而是从运行时拓扑和故障传播出发，检查每条链路能否长期稳定运行：

| 维度 | 检查内容 |
|---|---|
| 拓扑 | 前端、云端 API、本地 Bridge、桌面应用、平台账号之间的依赖是否清楚 |
| 状态源 | 账号状态、任务状态、额度状态是否有唯一可信来源 |
| 状态机 | queued/running/succeeded/failed/cancelled/needs_login 是否有合法迁移 |
| 幂等性 | 重复点击、重启、超时重试会不会重复发布或重复互动 |
| 重试 | 是否有退避、上限、不可重试错误分类和人工接管 |
| 读回 | 是否以平台真实结果作为成功依据，而不是以本地进程返回作为成功依据 |
| 恢复 | 进程崩溃、机器重启、网络中断、账号失效后能否恢复或明确停止 |
| 隔离 | 多租户、多账号、多任务是否会串数据、串权限或串凭据 |
| 观测 | 日志、审计、任务证据、诊断包是否足够定位问题 |
| 发布 | 安装、升级、回滚、签名和本地服务启动是否可重复验证 |

这套方法比较“能不能在真实环境中持续稳定地跑”，适合发现启动超时、竞态、重复副作用、错误状态、数据隔离和升级回滚问题。

两套方法必须交叉使用：任务链路通过但运行时不可靠，不能判为商用；运行时结构完整但外部平台没有真实结果，也不能判为商用。

## 3. 证据等级与判定规则

| 等级 | 证据 | 可用于商用判定 |
|---|---|---|
| A | Windows/macOS 真机、真实账号、真实平台外部结果、任务回读和截图/日志齐全 | 可以作为发布门槛证据 |
| B | 打包应用集成测试、真实本地 Bridge、模拟或沙箱平台结果 | 可以作为工程回归证据，不能独立证明真实运营 |
| C | 后端、前端、桌面端源码和自动化测试存在 | 只能证明已实现部分结构 |
| D | 页面、按钮、路由、文案或静态资源存在 | 不证明能力已实现 |

必须遵守：

- 没有外部平台结果，不能把“已发布”写成成功。
- 没有真实账号验证，不能把“已登录”写成可执行。
- 只有 D 级证据的能力，统一标记为“展示能力/待验证”。
- 任何失败状态必须包含原因、下一步动作和可追踪任务 ID。

## 4. 合规与清洁室边界

### 允许使用的输入

- 公开产品页面、公开帮助文档、公开平台规则。
- 用户可见的交互行为、输入输出、错误信息和性能表现。
- JIUZHANG 自有代码、日志、测试、架构和用户需求。
- 通过真实账号执行后获得的外部平台结果。

### 禁止使用的输入

- 反编译、复制或改写参考产品的源码、字节码、安装包内资源和私有接口。
- 复制对方的品牌、图标、文案、视觉资源、私有协议、凭据或账号数据。
- 将参考产品的内部实现当作 JIUZHANG 的实现方案。

### 清洁室记录

每个新增能力登记：需求来源、公开行为、独立设计、实现文件、测试证据和平台规则依据。对标只回答“用户需要什么结果”和“稳定性需要哪些工程属性”，不回答“如何复刻对方内部实现”。

## 5. 对比范围

### 5.1 核心任务矩阵

| 任务 | 参考产品观察重点 | JIUZHANG 当前判定 | 商用优先级 |
|---|---|---|---|
| 安装、启动、升级 | 首次启动、端口就绪、失败提示、自动更新 | v1.1.60 已补本地密钥和启动诊断；仍需 Windows 真机回归 | P0 |
| 平台账号绑定与刷新 | 抖音、快手、小红书、视频号账号识别和状态刷新 | 页面和账号模型存在；视频号绑定状态曾出现弹窗已绑定但列表不显示问题，需真机闭环 | P0 |
| 内容创建 | 图文、笔记、脚本、素材、模板 | 前端入口和后端模块较完整；需验证产物、保存、恢复和权限 | P1 |
| 多平台发布 | 草稿、定时、发布、回读、失败重试 | 已有多平台适配器与发布中心；真实发布授权、回读和回滚仍需验收 | P0 |
| 发布任务治理 | 队列、取消、重试、历史、证据 | Local Bridge 已有动作定义；协同取消、durable worker 和真实 Electron E2E 仍有缺口 | P0 |
| 微信联系人/群/朋友圈 | 联系人同步、搜索、私聊、群发、朋友圈 | 当前代码明确提示暂不支持桌面微信自动化；属于主要差距 | P0/P1，需单独合规评估 |
| 社交互动 | 评论、点赞、私信、关注、加好友、通过申请 | 参考产品能力较深；JIUZHANG 需区分“可发布”“可互动”和“需要人工确认” | P0 |
| 客户管理 | 线索、客户、跟进、标签、任务 | JIUZHANG 有 CRM/客户模块；需核验与真实互动结果关联 | P1 |
| AI 员工/专家 | 任务拆解、工具调用、审批、执行回读 | 当前更偏工作流和执行基础设施；需定义可承诺的最小闭环 | P1 |
| 视频与换脸 | 视频工作坊、视频发布、换脸 | 用户已要求前端隐藏，当前不纳入本轮商用验收；后端仍需权限隔离 | P2 |
| 移动端 | 安卓可独立完成的任务、审批、查看、轻编辑 | PWA/移动路由存在；重发布、桌面自动化和本地 Bridge 不应假装可独立完成 | P1 |
| 商业化基础设施 | 计费、额度、租户、审计、备份、回滚 | 工程基础存在；生产计费、隔离回归、备份恢复和发布回滚仍需验证 | P0 |

### 5.2 运行时可靠性矩阵

| 故障场景 | 预期行为 | 当前重点 |
|---|---|---|
| 本地 3011 未就绪 | 等待、诊断、限次重试，不显示空白页或无限加载 | v1.1.60 已修复核心启动问题，需 Windows 真机回归 |
| 平台登录过期 | 任务进入 needs_login，提示对应账号，不误报成功 | 账号状态刷新和视频号状态同步需重点验证 |
| 云端额度冻结 | 阻止执行并明确展示额度/冻结原因 | 需要和授权、计费、租户权限统一 |
| 网络中断 | 保留任务和幂等键，恢复后继续或明确失败 | 需验证发布与互动副作用不重复 |
| 平台拒绝/风控 | 不盲目重试，保留原始错误和人工处理入口 | 需要按平台分类错误 |
| 应用重启 | 恢复未完成任务或标记为可恢复 | durable worker 和 Electron E2E 是缺口 |
| 重复点击发布 | 同一业务动作只产生一个外部副作用 | 需要真实平台回读验证 |
| 多租户访问 | 租户 A 无法读写租户 B 的账号、内容、任务和凭据 | 需要回归测试和审计证据 |
| 升级失败 | 保留可启动版本，可回滚，用户可看见下一步 | 需 Windows 安装、升级、回滚实测 |
| 账号删除/解绑 | 清理任务引用和凭据，历史记录按合规策略保留 | 需要检查账号与任务的关联清理 |

## 6. 阶段计划与闸门

### 阶段 0：范围与授权冻结

产出：本方案、清洁室记录、能力分级、商用授权决策。  
闸门：没有明确授权边界，不进行参考产品代码或资源层面的复用。

当前状态：已移除仓库中的 Personal Use Only 许可声明，并将第一方包标记为 `UNLICENSED`；这不等于已经获得商业授权，正式商业许可文本仍需由权利人确定。

### 阶段 1：两套方法完成对比

产出：

- 用户任务链路矩阵。
- 运行时可靠性矩阵。
- 证据登记表，标明 A/B/C/D 等级。
- JIUZHANG 与参考产品的差距清单。

做法：先用已有源码、打包测试、安装包静态观察和现有交接文档完成 C/D 级初判；再把所有需要真实账号、Windows 真机或云端权限的项目列为人工验收项，不把未执行项写成已完成。

闸门：所有 P0 项目必须有明确的“已验证/未验证/不支持/需人工确认”结论。

### 阶段 2：四条最小商用闭环

优先闭环：

1. Windows 安装、启动、升级和诊断。
2. 账号绑定、刷新、登录失效和重新授权。
3. 内容创建到至少一个平台真实发布、回读和失败恢复。
4. 真实互动任务的授权、人工确认、执行、回读和审计。

不在四条闭环达标前扩张平台数量或堆叠页面入口。

闸门建议：每条闭环至少连续 20 次成功/预期失败场景回归；真实副作用操作必须有人工确认、任务 ID 和结果证据。

### 阶段 3：可靠性与商业基础设施

补齐：

- durable worker、取消语义、幂等键和可恢复任务。
- 统一账号状态机、额度/冻结状态机和权限判断。
- 多租户隔离、审计、凭据清理、备份恢复。
- 计费生产验收、额度扣减、退款/失败补偿。
- Windows 代码签名、安装器升级、回滚和版本发布流程。
- lint 警告收敛，先处理会掩盖运行时错误的 56 条警告。

闸门：故障注入、重启恢复、升级失败回滚和跨租户回归均有证据。

### 阶段 4：能力扩展

按商业价值逐项评估：

- 微信桌面自动化及其合规边界。
- 抖音/小红书/视频号的互动能力。
- 客户线索、跟进和互动结果的统一关联。
- 安卓端可独立完成的审批、轻编辑、任务监控和结果查看。

视频工作坊和换脸功能按用户当前要求继续隐藏，不纳入本轮前端验收；不可因为隐藏而绕过后端权限和数据隔离测试。

## 7. 商用判定标准

达到以下条件才允许对外宣称“商用可用”：

1. 安装、启动、升级、登录失败和本地服务故障有明确用户级处理路径。
2. 至少四条核心闭环具备 A 级真实证据。
3. 外部平台成功结果可回读，假成功率必须为 0。
4. 任务具备幂等、重试边界、取消语义和失败可定位性。
5. 多租户、账号、凭据、额度和审计完成回归。
6. Windows 真机安装和升级通过，且有可用的签名与回滚方案。
7. 计费、额度冻结、失败补偿和人工客服接管路径已验收。
8. 用户看不到未授权却可点击的执行入口；隐藏能力和后端权限一致。
9. 商业授权文本、第三方许可证和发布包清单明确。

## 8. 不立即做的事情

- 不复制炼刀的源码、资源、私有接口、私有协议或账号数据。
- 不以“页面已经有入口”替代真实能力验收。
- 不在真实账号授权、云端额度或 Windows 真机条件未满足时伪造成功结论。
- 不先做大规模 UI 重构来掩盖执行链路和状态机问题。
- 不把视频/换脸重新暴露到前端，除非用户重新确认范围。

## 9. 下一步执行顺序

1. 完成本文件对应的用户任务矩阵和运行时可靠性矩阵。
2. 对每个差距标注证据等级、优先级、负责人、依赖和验收方式。
3. 先验证 Windows 启动、账号状态、发布回读和互动授权四条 P0 闭环。
4. 输出“保留、修复、暂不支持、需要人工”的最终能力清单。
5. 只有在对比结果冻结后，进入代码实现；每次实现必须绑定一个矩阵项和一条验收证据。
